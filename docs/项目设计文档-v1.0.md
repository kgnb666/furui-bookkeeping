## 0. 文档摘要与关键结论

本文档是大学生个人记账系统的设计基线，只做设计与分析，不包含业务代码实现。

本阶段的关键结论如下：

1. **项目定位**：面向在校大学生的日常记账 App，目标是"真实可用 + 课程设计合理规模"。不引入微服务、消息队列、缓存中间件、容器编排、DDD 领域分层等与课程设计无关的技术。
2. **新增核心功能**：微信 / 支付宝账单导入。实现方式为**用户自行从官方渠道导出账单文件 → 上传到本系统 → 后端解析 → 预览确认 → 写入账本**。不涉及任何私有接口、逆向、Hook 或模拟登录。
3. **账单真实格式已核实**（2026-09 通过公开开源解析器与真实账单样例核对，详见第 8 章与附录 A）：
   - 微信"用于个人对账"账单为 **CSV，UTF-8**，正文前有 16 行说明信息，业务表头为 `交易时间,交易类型,交易对方,商品,收/支,金额(元),支付方式,当前状态,交易单号,商户单号,备注`，金额形如 `¥28.16`。
   - 支付宝"用于个人对账"账单为 **CSV，GBK/GB18030 编码**，正文前有回单说明，业务表头为 `交易时间,交易分类,交易对方,对方账号,商品说明,收/支,金额,收/付款方式,交易状态,交易订单号,商家订单号,备注`，金额形如 `20.00` 且列名与数据都带大量空格。
   - 两个平台的**商户版账单表头完全不同**（如"微信支付单号、商户订单号、交易金额(元)"），本系统明确不支持，需要识别并给出提示。
4. **解析策略**：不按固定列下标读取，而是**扫描表头行 + 列名映射**，同时做编码探测（UTF-8 / GB18030）与单元格清洗（空格、制表符、`¥`、千分位）。这样能同时兼容两个平台，并对平台格式的小幅调整有容错。
5. **去重策略**：以`来源 + 原始交易号`为首选去重键，无交易号时退化为`来源 + 交易时间 + 金额 + 交易对象 + 收支`的指纹；数据库对 `(user_id, dedup_key)` 建唯一索引兜底，预览阶段提前标记重复记录并默认不导入。
6. **金额规范**：后端一律 `BigDecimal`，数据库一律 `DECIMAL(10,2)`，金额恒为正数、方向由交易类型表达；**金额的加减与统计全部在后端完成**，接口以字符串形式返回金额，前端只负责展示，从根源上避免浮点误差。
7. **安全隔离**：所有账单、预算、统计接口的 `user_id` 只来自 JWT 解析结果，绝不接受前端传入；按 id 操作时统一使用 `WHERE id = ? AND user_id = ?`，越权访问返回 404。
8. **本机环境现状（重要）**：MySQL 8.0 已安装且 `MySQL80` 服务正在运行；但**当前机器上没有 JDK、Maven、Flutter SDK 与 Android SDK**。Stage 1 开始前需要先补齐环境，或调整前端运行目标（详见第 22 章与第 24 章）。
9. **第一版分类方案**：系统内置 10 个支出分类 + 5 个收入分类，采用"关键词匹配 + 支付宝自带交易分类映射"的方式推荐分类，用户可在导入预览中手动修改。不引入任何 AI / 机器学习分类。

## 1. 项目背景

### 1.1 背景

大学生在校期间的生活费来源相对固定（家庭转账、奖助学金、兼职收入），支出则集中在餐饮、零食奶茶、交通、网购、娱乐、学习资料、水电住宿等少数几类。这类消费具有**单笔金额小、笔数多、以移动支付为主**的特点。

移动支付使得"钱花在哪了"变得越来越模糊：学生打开微信和支付宝账单，能看到的是一长串流水，但无法回答"这个月餐饮花了多少""这个月还剩多少预算"这类问题。手工记账又因为笔数多而难以坚持。

因此，一个对大学生真正有用的记账系统，必须解决两个问题：

1. 记账要尽量省事——最好能把手头已有的微信 / 支付宝账单直接变成账本记录。
2. 要能看清钱花在哪里——月度收支、分类占比、每日趋势、预算执行情况。

### 1.2 项目性质

本项目是计算机类专业课程设计 / 平时作业，规模控制在"一个学生用一到两个月可以完整做完并跑通"的范围内。因此：

- 功能要完整且真实可用，不做只有界面没有逻辑的空壳功能；
- 技术栈要主流、资料多、容易排错，不追求技术炫耀；
- 架构要简单直接，避免为了抽象而抽象。

## 2. 项目目标与范围边界

### 2.1 目标

做一个大学生可以日常使用的个人记账 App，具备：

| 目标 | 说明 |
| --- | --- |
| 真实记账 | 支持手动新增 / 编辑 / 删除账单，数据真实落库 |
| 真实导入 | 能解析真实的微信 / 支付宝账单文件并批量转成账本记录 |
| 重复可控 | 同一批账单重复导入不会产生重复记录 |
| 真实统计 | 月度收支、分类统计、每日趋势、来源统计均由数据库真实聚合得出 |
| 预算可用 | 支持月度预算与分类限额，能提示使用进度与超支 |
| 数据隔离 | 每个用户只能访问自己的数据，且由后端强制保证 |
| 前后端可运行 | Spring Boot 后端 + Flutter 客户端可真实启动、真实联调 |

### 2.2 明确不做的事情（范围外）

这部分与"做什么"同等重要，用于防止后期需求膨胀：

| 范围外内容 | 原因 |
| --- | --- |
| 对接微信 / 支付宝私有接口、逆向、Hook、模拟登录 | 违反平台规则且无技术必要 |
| 破解加密压缩包 | 账单压缩包密码由平台下发给用户本人，应由用户自行解压 |
| 商户版 / 商家账单解析 | 表头与个人账单完全不同，属于另一类业务 |
| 银行卡、信用卡、云闪付账单解析 | 第一版不做，保持解析器数量可控 |
| AI / 机器学习自动分类 | 关键词匹配已足够，引入 AI 与课程设计定位不符 |
| 多币种、汇率换算 | 大学生记账场景不需要 |
| 团队账本 / 家庭共享账本 | 增加权限复杂度，与"个人记账"定位不符 |
| 消息队列、缓存、微服务、容器编排、CQRS、事件溯源 | 过度设计 |
| 记账数据的导入导出以外的第三方服务集成 | 无必要 |

### 2.3 规模控制原则

后续所有阶段遵守：

- 不创建没有实际用途的 `Base` / `Manager` / `Factory` / `Helper` / `Utils` 类；
- 不为只有一种实现的逻辑强行抽接口，除非这个抽象确实被两处以上复用（例如账单解析器有微信、支付宝两种实现，抽接口是合理的）；
- 不写模板化的、没有信息量的注释和 Javadoc；
- 不为了"看起来专业"而拆表、拆层、拆服务。

## 3. 用户角色

本项目为单角色系统，不设管理员后台。

| 角色 | 说明 | 权限 |
| --- | --- | --- |
| 游客 | 未登录访问者 | 仅能访问注册、登录接口与对应页面 |
| 注册用户 | 系统的主要使用者（大学生本人） | 管理自己的账单、导入账单、查看自己的统计与预算、维护个人资料 |
| 演示账号 | 预置的演示用户（如 `demo`） | 与注册用户权限完全相同，仅用于答辩与功能演示 |

角色说明补充：

- 不存在"能查看所有人数据"的角色，数据库层也不提供这样的查询入口。
- 演示环境会额外预置第二个账号（如 `demo2`），用于现场演示"用户 A 看不到用户 B 的数据"。

## 6. 账单业务流程

### 6.1 账单数据模型（业务视角）

账单是系统的核心数据，一条账单包含以下语义：

| 业务字段 | 含义 | 说明 |
| --- | --- | --- |
| 交易类型 | 收入 / 支出 / 不计收支 | 决定金额方向；不计收支不参与收支统计 |
| 金额 | 交易金额 | **恒为正数**，方向由交易类型表达，避免出现 `-0` 与双重取负 |
| 分类 | 餐饮 / 交通 / 购物 …… | 支出与收入使用各自的分类集合 |
| 记账日期 | 交易发生的日期 | 手动记账默认当天；导入时取交易时间中的日期部分 |
| 交易对象 | 商家或对方名称 | 如"星巴克""滴滴出行" |
| 备注 | 商品说明 / 备注 | 导入时来自"商品说明"或"备注"列 |
| 来源 | 手动 / 微信 / 支付宝 | 用于筛选、来源统计与溯源 |
| 原始交易号 | 平台流水号 | 手动记账为空；用于去重与溯源 |

### 6.2 手动记账流程

```text
用户点击"记一笔"
    ↓
选择类型（支出 / 收入）
    ↓
输入金额（最多两位小数，且必须大于 0）
    ↓
选择分类
    ↓
选择日期（默认今天，不允许晚于今天）
    ↓
填写交易对象 / 备注（选填）
    ↓
提交 → 后端校验 → 写入 bill 表（source = MANUAL）
    ↓
返回账单列表页并刷新统计
```

校验规则：

- 金额必须 > 0，最多两位小数，上限 99,999,999.99；
- 分类必须在系统允许的分类集合内；
- 日期不能晚于当天（避免误填未来日期导致统计异常）；
- 备注与交易对象长度做上限限制（与数据库字段长度一致），避免插入报错。

### 6.3 账单管理流程

| 操作 | 业务规则 |
| --- | --- |
| 列表查询 | 只查当前用户；支持月份、类型、分类、来源、关键词、分页 |
| 详情查询 | `WHERE id = ? AND user_id = ?`；不存在或不属于当前用户统一返回 404 |
| 修改 | 先校验归属，再更新；导入产生的记录同样允许修改（用户可能想改分类） |
| 删除 | 先校验归属，再删除；删除导入记录不影响导入批次表的汇总数据 |

## 7. 微信 / 支付宝账单导入流程

### 7.1 设计前提

本系统**不登录用户的微信 / 支付宝账号**，也不调用任何非公开接口。账单文件完全由用户按官方流程自行获取：

| 平台 | 用户获取账单的官方路径（核实于 2026-09） | 交付形式 |
| --- | --- | --- |
| 微信支付 | 微信 → 我 → 服务（旧版为"支付"）→ 钱包 → 账单 → 右上角"常见问题" → 下载账单 → 选择"用于个人对账" → 选择时间范围 → 填写接收邮箱 | 邮件收到账单压缩包，解压后为 CSV 文件（部分版本提供 Excel） |
| 支付宝 | 支付宝 → 我的 → 账单 → 右上角"…" → 开具交易流水证明 → 申请用途选择"用于个人对账" → 选择时间范围 → 填写电子邮箱 | 邮件收到账单压缩包，解压后为 CSV 文件 |

关键约束：

1. 两个平台都通过**邮箱下发压缩包**，而不是在 App 内直接下载；
2. 微信的压缩包可能带解压密码，密码由微信支付通过消息下发；
3. 因此**第一版要求用户自行解压，上传解压后的 CSV / XLSX 文件**。系统不处理加密压缩包，也不尝试破解密码（见第 24 章决策点）。

## 8. 文件解析方案

### 8.1 账单真实格式核实结论

本阶段没有主观假定格式，而是通过公开开源账单解析器仓库中的**真实导出账单样例**与解析实现进行了核对（核对记录见附录 A），结论如下。

#### 8.1.1 微信"用于个人对账"账单（CSV）

- **编码**：UTF-8
- **结构**：正文前有若干行说明信息，业务表头在其后
- **表头列（共 11 列）**：

```text
交易时间,交易类型,交易对方,商品,收/支,金额(元),支付方式,当前状态,交易单号,商户单号,备注
```

- **数据示例（已脱敏）**：

```text
2019-09-26 12:45:27,"商户消费","云膳过桥米线(传奇广场店)","总共消费:28.16","支出",¥28.16,"中国银行(1234)","支付成功","3985734"	,"129847129"	,"/"
2019-09-24 10:10:11,微信红包,同性好友,/,收入,¥0.35,/,已存入零钱,3985734	,129847129	,/
2021-01-17 10:07:31,转入零钱通-来自工商银行(9876),/,/,/,¥2000.00,工商银行(9876),支付成功,3985734,129847129,/
2021-07-15 16:29:37,零钱提现,招商银行(),"/",/,¥100.10,工商银行,提现已到账,207210715100077148235523883175	,/	,"服务费¥0.10"
```

- **必须处理的真实脏数据**：
  1. 字段值可能带**制表符**（`"3985734"\t`），必须 trim；
  2. 双引号使用不一致，同一文件里既有带引号的值也有裸值；
  3. `收/支` 除了"收入""支出"，还有 `/`（中性交易）；
  4. 金额带 `¥` 前缀；
  5. 交易单号 / 商户单号可能为空或为 `/`。

#### 8.1.2 支付宝"用于个人对账"账单（CSV）

- **编码**：**GBK / GB18030**（与微信不同，这是最容易踩坑的地方）
- **结构**：正文前有回单导出信息与"特别提示"，业务表头之后为数据行，末尾有空行
- **表头列（共 12 列，行尾还有一个空列）**：

```text
交易时间            ,交易分类                ,交易对方                ,对方账号                ,商品说明                ,收/支                 ,金额                  ,收/付款方式              ,交易状态                ,交易订单号     ,商家订单号           ,备注                  ,
```

- **数据示例（已脱敏）**：

```text
2023-02-12 21:32:14 ,亲友代付                ,xxxxxxxxxxxx          ,/                   ,亲情卡                 ,支出                  ,49.74               ,交通银行信用卡(7449)       ,交易成功                ,202302xxxxxx0011000103xxxxxx	,20230xxxxxxx014741014xxxxxx	,                    ,
2023-02-08 14:16:52 ,日用百货                ,x4***6               ,rim***@qq.com    ,商品示例   ,支出                  ,20.00               ,余额                  ,等待确认收货              ,2xxxxxxxxxxxxxx0	,Txxxxxxxxxxxxx0	,                    ,
2023-02-04 18:21:04 ,退款                  ,xxxxxxx         ,/                   ,退款-亲情卡              ,不计收支                ,16.03               ,交通银行信用卡(7449)       ,退款成功                ,2xxxxxxxxxxxxxxxx8	,20xxxxxxxxxxxxxxxx5	,                    ,
2023-01-09 18:22:28,退款,一卡通,fin***@jieyisoft.com,退款-一卡通充值,不计收支,50.00,余额宝,退款成功,2023xxxxx88_2023xx57	,D12*****14	,,
```

- **必须处理的真实脏数据**：
  1. **编码为 GBK**，用 UTF-8 读取会直接乱码；
  2. 表头与数据带**大量对齐空格**，必须对列名与值同时 trim；
  3. 行尾有**空列**，列数需要按表头对齐而不是按行硬切；
  4. 字段值可能带**制表符**；
  5. `收/支` 存在第三种取值"**不计收支**"（充值、提现、转账、退款、理财等）；
  6. `金额` 无货币符号，但可能带空格，且不同行空格数量不一致；
  7. 不同行的列宽不一致（有的行末尾逗号展开、有的没有），必须容忍。

#### 8.1.3 明确不支持的格式

**商户版账单的表头与个人账单完全不同**，例如：

```text
微信商户账单：...,微信支付单号,商户订单号,...,交易金额(元),...,交易状态,...
支付宝商户账单：支付宝交易号,商户订单号,...,订单金额（元）,...,服务费（元）,...
```

系统在解析时若发现表头不满足个人账单特征，直接返回明确错误："该文件不是'用于个人对账'的账单文件，请导出个人对账账单后重试"，而不是尝试兜底解析。

同时，账单文件还可能是网页版"下载查询结果"导出的较早格式（列包含"交易创建时间、付款时间、最近修改时间、交易来源地、服务费（元）"等）。第一版**不支持**该格式，但会在表头识别阶段明确区分并给出提示，而不是解析出错误数据。

### 8.2 解析策略：表头定位 + 列名映射

**不采用按固定列下标解析**，原因：

1. 两个平台的列顺序与列数不同；
2. 同一平台不同版本导出的列可能增减；
3. 固定下标一旦平台调整字段顺序，会静默解析出错误数据（例如把"商家订单号"当成"交易单号"），比直接报错更危险。

因此解析流程为四步：

```text
① 读取字节流 → 探测编码（BOM → UTF-8 → 失败则 GB18030）
        ↓
② 只扫描前 30 行，定位"业务表头行"
   判定条件：该行同时包含 "交易时间"、"金额"、"收/支"
        ↓
③ 用表头建立 Map<列名, 列下标>，文件中不存在的列按空值处理
        ↓
④ 逐行读取数据行：跳过空行与说明行
   （列数明显少于表头、或关键列全为空的行走"解析失败"分支）
```

解析类的职责边界：

| 类 | 职责 |
| --- | --- |
| `BillFileParser`（接口） | 声明 `boolean supports(String source)` 与 `List<ParsedBill> parse(InputStream)` |
| `WechatBillParser` | 按微信列名映射解析，识别 `收/支` 的三种取值 |
| `AlipayBillParser` | 按支付宝列名映射解析，使用支付宝"交易分类"作为分类提示 |
| `BillImportService` | 按来源选择解析器，编排"分类 → 查重 → 预览 / 入库" |

两个解析器只负责"把文件变成统一的 `ParsedBill` 列表"，不写数据库、不含业务规则，便于单独编写单元测试。

### 8.3 字段标准化规则

| 系统字段 | 微信列 | 支付宝列 | 标准化规则 |
| --- | --- | --- | --- |
| bill_date | 交易时间 | 交易时间 | 解析 `yyyy-MM-dd HH:mm:ss`，取日期部分；同时保留原始时间用于去重指纹 |
| type | 收/支 | 收/支 | `支出`→1；`收入`→2；`/`、`不计收支`、空→3（数据库存 1/2/3） |
| amount | 金额(元) | 金额 | 去空格与制表符 → 去 `¥`/`￥` → 去千分位逗号 → 转 `BigDecimal`，保留 2 位小数（四舍五入） |
| merchant | 交易对方 | 交易对方 | trim；空值或 `/` 置为空字符串 |
| remark | 商品 + 备注 | 商品说明 + 备注 | 两者非空时用空格拼接；值为 `/` 视为空 |
| pay_method | 支付方式 | 收/付款方式 | trim，作为辅助信息展示（第一版可选不入库） |
| trade_status | 当前状态 | 交易状态 | trim，用于识别退款等特殊情况 |
| source_trade_id | 交易单号 | 交易订单号 | trim；值为 `/` 或空时视为"无交易号"，转入备用去重规则 |
| merchant_order_id | 商户单号 | 商家订单号 | trim，仅用于溯源展示（可选扩展字段） |
| category_hint | —— | 交易分类 | 支付宝自带分类，映射到系统分类作为强提示 |

补充说明：

- **金额一律解析为绝对值正数**，方向由 `type` 决定，不做正负号推断；
- 退款处理：微信 `当前状态` 含"退款"、支付宝 `交易分类 = 退款` 或 `交易状态` 含"退款"时，第一版仍按 `收/支` 字段决定类型（支付宝退款一般标为"不计收支"），**不做复杂的退款冲销计算**（见第 22 章限制说明）；
- 时间解析失败的行计入"解析失败"，在预览页标注原因，不进入可导入列表；
- 金额解析失败的行同样计入"解析失败"，原因是金额字段清洗后无法转为数字。

### 8.4 编码探测实现方案

```text
读取文件前 3 字节
    ├── EF BB BF              → UTF-8 with BOM（解析前去掉 BOM）
    └── 其他情况：
         用 UTF-8 严格模式解码前若干 KB
              ├── 成功   → 整个文件按 UTF-8 解析
              └── 失败   → 整个文件按 GB18030 解析
```

说明：

- 使用 `CharsetDecoder` 配合 `CodingErrorAction.REPORT` 做严格判断，而不是"猜编码"；
- GB18030 是 GBK 的超集，可覆盖支付宝旧版账单；
- 编码探测与表头定位都放在后端，Flutter 端只上传原始字节流，避免客户端编码差异导致乱码。

### 8.5 文件与规模限制

| 限制项 | 取值 | 说明 |
| --- | --- | --- |
| 单文件大小 | ≤ 5 MB | 大学生几个月的账单通常只有几百 KB |
| 单次导入记录数 | ≤ 2000 条 | 超出时提示"请按月份分批导入" |
| 支持扩展名 | `.csv`、`.xlsx` | `.xlsx` 采用与 CSV 相同的列名映射逻辑，第一版优先级低于 CSV |
| 不支持 | `.zip`、`.xls`、加密文件 | 提示用户先解压或转换为 CSV |

### 8.6 安全与隐私要求

1. 上传文件**只在内存中解析**，不落盘保存，解析完成后立即丢弃原始字节；
2. 日志中**禁止打印账单原文**，最多记录"文件名、来源、总条数、成功条数"；
3. 文件名只用于展示，不参与任何路径拼接（防止路径穿越）；
4. 账单中的"对方账号"等字段**不入库**，避免存储无关的个人敏感信息；
5. 在导入页明确提示用户：账单文件包含真实姓名与账号信息，建议使用本人账号导出的文件，并在使用后自行删除邮件附件。

## 9. 自动分类方案

### 9.1 分类集合（固定，不建表）

分类数量少且稳定，因此**第一版不建 `category` 表**，直接在后端用常量维护，前端使用同一份常量：

| 分类类型 | 分类集合 |
| --- | --- |
| 支出分类（10 个） | 餐饮、交通、购物、娱乐、学习、住宿、生活、医疗、通讯、其他 |
| 收入分类（5 个） | 生活费、奖助学金、兼职收入、红包、其他收入 |

`其他` 与 `其他收入` 是兜底分类，保证任何交易都有分类可落。

### 9.2 匹配策略：关键词匹配 + 用户手动修改

```text
解析出的交易记录
    ↓
① 支付宝自带"交易分类"映射（如 日用百货 → 生活；交通出行 → 交通）
    ↓ 无结果时
② 关键词匹配"交易对方"（如 星巴克 → 餐饮）
    ↓ 无结果时
③ 关键词匹配"商品说明 / 备注"
    ↓ 无结果时
④ 按交易类型给兜底分类（支出 → 其他；收入 → 其他收入）
    ↓
⑤ 返回推荐分类 + 命中来源（便于用户判断是否可信）
    ↓
⑥ 用户在导入预览中逐条修改
```

关键词匹配规则：

- 匹配方式为**包含匹配**（`contains`），忽略大小写与首尾空格；
- 规则按优先级顺序存放，命中第一条即返回；
- 规则文件为 `resources/category-rules.txt`，格式为 `关键词|分类`，一行一条，便于后续增删。

| 兼职、家教、实习 | 兼职收入（收入） |

边界情况处理：

- 同一分类可对应多个关键词；
- 同一笔交易命中多个关键词时，取规则清单中靠前的一条，因此清单中把更具体的关键词放在前面（如"美团买菜"放在"美团"之前），避免把买菜误判为餐饮；
- 未命中任何规则时落到兜底分类，不再做二次推断。

### 9.4 用户自定义规则

第一版**只做系统内置关键词匹配**，不提供用户自定义规则的管理界面，理由：

- 自定义规则需要额外的规则表、增删改接口与冲突处理，会明显增加项目复杂度；
- 导入预览页已允许用户逐条修改分类，可覆盖"系统猜错"的场景。

如后续确实需要，只需新增一张规则表与两个接口即可（不影响现有表结构），列入可选扩展（见第 21 章）。

## 10. 去重方案

### 10.1 问题场景

```text
第一次导入：微信账单 2026-09-01 ~ 2026-09-15  → 100 条
第二次导入：微信账单 2026-09-01 ~ 2026-09-30  → 含前 100 条 + 后 15 条
```

第二次导入时，前 100 条必须被识别为重复，不能再次入库。

### 10.2 去重键设计

在 `bill` 表上增加 `dedup_key` 字段，取值规则：

| 优先级 | 条件 | dedup_key 计算方式 | 说明 |
| --- | --- | --- | --- |
| 首选 | 账单中存在稳定的原始交易号 | `来源型别:交易号`，如 `WECHAT:4200001234202609151234567890` | 微信取"交易单号"，支付宝取"交易订单号"，唯一性最好 |
| 备用 | 无交易号（值为 `/` 或空） | `来源型别:MD5(交易时间原值 \| 金额 \| 交易对象 \| 收支类型)`，如 `ALIPAY:9f2c...` | 组合字段指纹，用于没有稳定流水号的情况 |
| 不适用 | 手动记账 | `NULL` | MySQL 唯一索引允许多个 NULL，手动记录不受去重约束 |

设计要点：

- 计算去重键时使用**原始交易时间字符串**（精确到秒），而不是仅用日期，避免同一天多笔相同金额被误判；
- 金额参与指纹时使用**两位小数的标准字符串**（如 `31.00`），不使用浮点数，避免精度差异导致指纹不稳定；
- 指纹输入统一 trim，避免空格差异造成漏判；
- `dedup_key` 只含 ASCII 字符，可声明为 `VARCHAR(80) CHARACTER SET ascii` 以缩小索引体积。

### 10.3 数据库唯一约束

```sql
UNIQUE KEY `uk_bill_user_dedup` (`user_id`, `dedup_key`)
```

结论：**需要唯一约束**，原因：

1. 并发或重复提交（用户连点两次"确认导入"）时，应用层查询无法保证唯一，数据库约束是最后一道防线；
2. 唯一约束把"不产生重复记账"从"代码自觉"变成"数据库保证"；
3. 手动记录的 `dedup_key` 为 `NULL`，不会对手动记账造成任何限制；
4. 约束中包含 `user_id`，不同用户的相同交易互不影响。

### 10.4 两层查重流程

```text
【预览阶段：提前告知用户】
  1. 解析出 N 条记录并计算 dedup_key
  2. 收集本批全部 dedup_key
  3. 一次 SQL 批量查询：SELECT dedup_key FROM bill WHERE user_id = ? AND dedup_key IN (...)
  4. 命中库内已有记录 → 标记"与已有记录重复"
  5. 同一文件内出现相同 dedup_key → 仅保留第一条，其余标记"文件内重复"
  6. 返回预览：新增 / 重复 分组，重复项默认不勾选

【确认阶段：兜底】
  7. 只写入用户勾选的记录，逐条计算 dedup_key
  8. 插入时若触发唯一键冲突（DuplicateKeyException）→ 该条计入"重复跳过"，继续处理后续记录
  9. 整批导入在同一事务中完成，冲突行不影响其余记录入库
```

第 8 步采用"插入并捕获唯一键冲突"而不是"先查询再插入"，可以避免用户连点两次确认时的竞态问题。最终在导入结果中如实汇报"重复跳过 N 条"。

### 10.5 重复数据如何提示用户

| 场景 | 系统行为 |
| --- | --- |
| 预览中发现重复 | 预览页显示"重复记录：8 条"，重复项默认不勾选，可展开查看 |
| 用户仍勾选了重复项 | 确认导入时被唯一约束拦截，结果页计入"重复跳过" |
| 文件内部重复 | 预览页标记"文件内重复"，同样默认不勾选 |

### 10.6 已知局限（如实说明）

指纹去重存在理论上的**误判可能**：同一用户在同一秒、同一商家消费完全相同的金额两次，会被指纹判定为重复。这种情况在真实账单中极为罕见，且后果只是少导入一条记录，用户可手动补记。因此第一版不设计更复杂的去重算法（如多字段加权相似度匹配），以保持实现简单可靠。

## 11. 数据库设计

### 11.1 建表总体结论

- 数据库：MySQL 8.0
- 库名：`campus_ledger`
- 字符集：`utf8mb4` / `utf8mb4_general_ci`
- 表数量：**4 张**（`user`、`bill`、`budget`、`import_batch`）
- **不建 `category` 表**：分类固定且简单，用后端常量 + 前端常量维护即可，拆表只会增加联表查询与维护成本
- **不建 `bill_tag`、`bill_attachment`、`account` 等表**：当前需求不需要

### 11.2 表结构 DDL

```sql
-- 0. 建库
CREATE DATABASE IF NOT EXISTS campus_ledger
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_general_ci;

USE campus_ledger;

-- 1. 用户表
CREATE TABLE `user` (
  `id`         BIGINT       NOT NULL AUTO_INCREMENT              COMMENT '用户ID',
  `username`   VARCHAR(32)  NOT NULL                             COMMENT '登录名',
  `password`   VARCHAR(100) NOT NULL                             COMMENT 'BCrypt 加密后的密码',
  `nickname`   VARCHAR(32)  NOT NULL DEFAULT ''                  COMMENT '昵称',
  `email`      VARCHAR(64)      NULL                             COMMENT '邮箱（选填）',
  `created_at` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_username` (`username`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '用户表';

-- 2. 账单表
CREATE TABLE `bill` (
  `id`              BIGINT        NOT NULL AUTO_INCREMENT          COMMENT '账单ID',
  `user_id`         BIGINT        NOT NULL                         COMMENT '所属用户ID',
`type`            TINYINT       NOT NULL                         COMMENT '1=支出 2=收入 3=不计收支',
  `amount`          DECIMAL(10,2) NOT NULL                         COMMENT '金额，恒为正数，方向由 type 决定',
  `category`        VARCHAR(20)   NOT NULL                         COMMENT '分类名称',
  `bill_date`       DATE          NOT NULL                         COMMENT '记账日期',
  `merchant`        VARCHAR(64)   NOT NULL DEFAULT ''              COMMENT '交易对象/商家',
  `remark`          VARCHAR(255)  NOT NULL DEFAULT ''              COMMENT '备注/商品说明',
  `source`          VARCHAR(10)   NOT NULL DEFAULT 'MANUAL'        COMMENT 'MANUAL=手动 WECHAT=微信 ALIPAY=支付宝',
  `source_trade_id` VARCHAR(64)       NULL                         COMMENT '平台原始交易号（微信交易单号/支付宝交易订单号）',
  `dedup_key`       VARCHAR(80) CHARACTER SET ascii NULL           COMMENT '去重键，手动记录为 NULL',
  `import_batch_id` BIGINT            NULL                         COMMENT '导入批次ID，手动记账为 NULL',
  `created_at`      DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`      DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_bill_user_dedup`    (`user_id`, `dedup_key`),
  KEY        `idx_bill_user_date`    (`user_id`, `bill_date`),
  KEY        `idx_bill_user_type_date` (`user_id`, `type`, `bill_date`),
  KEY        `idx_bill_user_category` (`user_id`, `category`),
  KEY        `idx_bill_user_source`  (`user_id`, `source`),
  KEY        `idx_bill_batch`        (`import_batch_id`),
  CONSTRAINT `fk_bill_user`  FOREIGN KEY (`user_id`) REFERENCES `user` (`id`) ON DELETE CASCADE,
  CONSTRAINT `fk_bill_batch` FOREIGN KEY (`import_batch_id`) REFERENCES `import_batch` (`id`) ON DELETE SET NULL
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '账单表';

-- 3. 预算表
CREATE TABLE `budget` (
  `id`         BIGINT        NOT NULL AUTO_INCREMENT            COMMENT '预算ID',
  `user_id`    BIGINT        NOT NULL                           COMMENT '所属用户ID',
  `month`      CHAR(7)       NOT NULL                           COMMENT '预算月份，格式 yyyy-MM',
  `category`   VARCHAR(20)   NOT NULL DEFAULT ''                COMMENT '空串=月度总预算，否则为分类限额',
  `amount`     DECIMAL(10,2) NOT NULL                           COMMENT '预算金额',
  `created_at` DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at` DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_budget_user_month_category` (`user_id`, `month`, `category`),
  CONSTRAINT `fk_budget_user` FOREIGN KEY (`user_id`) REFERENCES `user` (`id`) ON DELETE CASCADE
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '预算表';

-- 4. 导入批次表
CREATE TABLE `import_batch` (
  `id`              BIGINT       NOT NULL AUTO_INCREMENT        COMMENT '批次ID',
  `user_id`         BIGINT       NOT NULL                       COMMENT '所属用户ID',
  `source`          VARCHAR(10)  NOT NULL                       COMMENT 'WECHAT / ALIPAY',
  `file_name`       VARCHAR(128) NOT NULL                       COMMENT '上传的账单文件名（仅展示）',
  `total_count`     INT          NOT NULL DEFAULT 0             COMMENT '解析出的总条数',
  `imported_count`  INT          NOT NULL DEFAULT 0             COMMENT '成功导入条数',
  `duplicate_count` INT          NOT NULL DEFAULT 0             COMMENT '重复跳过条数',
  `failed_count`    INT          NOT NULL DEFAULT 0             COMMENT '解析失败条数',
  `created_at`      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_batch_user_created` (`user_id`, `created_at`),
  CONSTRAINT `fk_batch_user` FOREIGN KEY (`user_id`) REFERENCES `user` (`id`) ON DELETE CASCADE
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '账单导入批次表';
```

建表顺序说明：`bill` 表引用了 `import_batch`，因此实际执行时先建 `user`、`import_batch`，再建 `bill`、`budget`。提供的初始化脚本会按正确顺序执行。

### 11.3 字段设计说明

| 表 | 字段 | 类型选择理由 |
| --- | --- | --- |
| user | password | `VARCHAR(100)`，存放 BCrypt 哈希（60 字符），留出余量以便将来更换算法 |
| user | username | 唯一索引，登录名不允许重复 |
| bill | type | `TINYINT`（1/2/3），比 `VARCHAR` 省空间，且便于按类型建联合索引 |
| bill | amount | `DECIMAL(10,2)`，范围 0.01 ~ 99,999,999.99，**严禁使用 float/double** |
| bill | bill_date | `DATE`，统计按天/按月分组，不需要时间精度 |
| bill | source | `VARCHAR(10)`，取值 `MANUAL`/`WECHAT`/`ALIPAY`，用字符串而不是数字是为了查询与排查直观 |
| bill | source_trade_id | `VARCHAR(64)`，微信交易单号为 28~32 位数字，支付宝订单号可能更长且含下划线 |
| bill | dedup_key | `VARCHAR(80) CHARACTER SET ascii`，仅含 ASCII，用 ascii 字符集可显著缩小唯一索引体积 |
| bill | merchant / remark | 长度按账单实际内容设定（64 / 255），避免过长导致索引与存储浪费 |
| budget | month | `CHAR(7)`，固定 `yyyy-MM`，比 DATE 更直观，且能直接做唯一约束 |
| budget | category | 用**空串**表示"月度总预算"，而不是 `NULL`，因为 MySQL 唯一索引中多个 `NULL` 不算冲突，用空串才能保证"一个用户一个月只有一条总预算" |

### 11.4 索引设计说明

| 索引 | 服务的查询 |
| --- | --- |
| `uk_bill_user_dedup` | 导入去重的唯一性保证（同时服务批量查重） |
| `idx_bill_user_date` | 账单列表按月份/日期范围查询、每日趋势统计 |
| `idx_bill_user_type_date` | 月度收支统计（按类型 + 日期范围聚合） |
| `idx_bill_user_category` | 分类统计 |
| `idx_bill_user_source` | 来源统计 |
| `idx_batch_user_created` | 导入批次历史按时间倒序查询 |

所有索引都以 `user_id` 开头，因为**几乎所有查询都带 `user_id` 条件**，符合数据隔离设计。

### 11.5 关于外键的说明

本设计**使用物理外键**（`FOREIGN KEY`），理由是：

1. 关系简单明确（用户 → 账单/预算/批次），物理外键能真实保证引用完整性，成本很低；
2. 答辩与检查时，"数据库层真的有关系约束"比只在应用层维护更有说服力；
3. 不存在高并发写入场景，外键带来的性能开销可以忽略。

删除策略：

- `user` 被删除时，级联删除其账单、预算、批次（`ON DELETE CASCADE`）；
- `import_batch` 被删除时，账单的 `import_batch_id` 置为 `NULL`（`ON DELETE SET NULL`），账单本身保留。

## 13. 后端架构

### 13.1 分层与职责

```text
HTTP 请求
   ↓
AuthInterceptor（除白名单外，校验 JWT 并解析出 currentUserId）
   ↓
Controller   仅做：参数接收、参数校验、调用 Service、包装统一响应
   ↓
Service      业务规则、归属校验、事务边界、调用 Mapper 与解析器
   ↓
Mapper       MyBatis-Plus 单表操作 + XML 中的统计聚合 SQL
   ↓
MySQL
```

各层约束：

- Controller 不写 SQL、不写业务分支；
- Service 不直接操作 `HttpServletRequest`，当前用户通过 `CurrentUser`（ThreadLocal）获取；
- Mapper 中的每一条查询都显式带 `user_id` 条件，禁止出现"只按 id 查询账单"的方法。

### 13.2 统一响应体

```json
{
  "code": 200,
  "message": "success",
  "data": { }
}
```

| 字段 | 说明 |
| --- | --- |
| code | `0` 表示成功；失败时取 HTTP 状态码（400 / 401 / 404 / 409 / 500） |
| message | 面向用户的可读提示（中文） |
| data | 业务数据；无数据时为 `null` |

统一错误码：

| 状态码 | 场景 | 示例提示 |
| --- | --- | --- |
| 200 | 成功 | success |
| 400 | 参数校验失败 | 金额必须大于 0 |
| 401 | 未登录 / Token 失效 | 登录已过期，请重新登录 |
| 404 | 资源不存在或不属于当前用户 | 账单不存在 |
| 409 | 冲突 | 用户名已存在 / 该账单已导入过 |
| 413 | 文件过大 | 文件大小超过 5MB |
| 500 | 服务器异常 | 服务器开小差了，请稍后重试 |

### 13.3 异常处理

```text
BizException（业务异常，携带状态码与提示）
        ↓
GlobalExceptionHandler（@RestControllerAdvice）
    ├── BizException            → 返回对应状态码与提示
    ├── MethodArgumentNotValidException → 400 + 第一条校验错误
    ├── MaxUploadSizeExceededException  → 413
    └── Exception               → 500，日志记录堆栈，对外不暴露细节
```

业务异常只用于"可以预期"的情况（校验失败、账号重复、无权访问）；其他异常统一走 500 并写日志。

### 13.4 事务边界

| 操作 | 事务 | 说明 |
| --- | --- | --- |
| 注册用户 | 单条插入，无需显式事务 | |
| 新增 / 修改 / 删除账单 | 单表单条，使用默认事务 | |
| 确认导入 | `@Transactional` | 先写 `import_batch`，再逐条插入 `bill`，最后回写批次统计 |

导入的重复行处理方式：逐条插入时捕获唯一键冲突异常并跳过。由于 Spring 的事务在遇到异常后可能被标记为回滚，实现上采用"**逐条插入 + 冲突行单独处理**"的方式：命中唯一键冲突时不抛到事务外，仅跳过该条并累加计数，保证整批导入正常提交（具体实现细节在 Stage 2 编码时确定，本阶段明确该行为要求）。

### 13.5 认证实现要点

| 项 | 方案 |
| --- | --- |
| Token 类型 | JWT（HS256），payload 只放 `userId` 与 `username` |
| 有效期 | 7 天 |
| 密钥 | 配置在 `application.yml`，不硬编码在代码里 |
| 密码存储 | BCrypt 哈希（引入 `spring-security-crypto` 单模块，不引入完整 Spring Security，保持简单） |
| Token 传递 | 请求头 `Authorization: Bearer <token>` |
| 白名单 | `/api/auth/**` |
| 失效处理 | 拦截器返回 401 + "登录已过期，请重新登录"，前端清除本地 Token 并跳转登录页 |

### 13.6 关键配置项

```yaml
server:
```

## 16. 权限设计

### 16.1 核心原则

> 用户只能看到和修改自己的数据，且该限制**必须由后端保证**，前端隐藏按钮只是体验优化。

### 16.2 实现方式

| 环节 | 做法 |
| --- | --- |
| 身份来源 | 仅来自 JWT。拦截器解析 Token 得到 `userId`，放入 `CurrentUser`（ThreadLocal），请求参数中**不允许出现 userId** |
| 查询条件 | 所有账单 / 预算 / 统计查询强制追加 `user_id = 当前用户` 条件 |
| 按 id 操作 | 统一使用 `WHERE id = ? AND user_id = ?`，而不是"先查出来再判断归属" |
| 越权响应 | 记录不存在或不属于当前用户，**统一返回 404 "账单不存在"**，不返回 403，避免泄露"该 id 存在但不属于你"的信息 |
| 写入校验 | 新增/修改账单时，`user_id` 一律取当前登录用户，忽略请求体中任何用户字段 |
| 导入校验 | 导入预览与确认接口同样只作用于当前用户；确认时服务端重新计算去重键并校验每条记录 |
| 批次归属 | 导入批次查询同样带 `user_id` 条件 |

### 16.3 关键 SQL 形态

```sql
-- 列表：只查当前用户
SELECT * FROM bill WHERE user_id = ? AND bill_date BETWEEN ? AND ? ORDER BY bill_date DESC, id DESC LIMIT ?, ?;

-- 详情：必须带 user_id
SELECT * FROM bill WHERE id = ? AND user_id = ?;

-- 更新：必须带 user_id
UPDATE bill SET type = ?, amount = ? WHERE id = ? AND user_id = ?;

-- 删除：必须带 user_id
DELETE FROM bill WHERE id = ? AND user_id = ?;

-- 统计：所有聚合都带 user_id
SELECT category, SUM(amount) FROM bill WHERE user_id = ? AND type = 1 AND bill_date BETWEEN ? AND ? GROUP BY category;
```

### 16.4 权限测试要求（Stage 5/6 必做）

1. 用 `demo` 登录，`GET /api/bills` 只返回 demo 的账单；
2. 用 `demo` 的 Token 访问 `demo2` 的账单 id → 返回 404；
3. 用 `demo` 的 Token 调用 `PUT /api/bills/{demo2的id}` → 返回 404 且数据未被修改；
4. 请求中伪造 `userId` 字段 → 被忽略，仍然只操作自己的数据；
5. 无 Token / 过期 Token 访问任意业务接口 → 401。

### 16.5 前端职责边界

Flutter 端的权限处理只包括：未登录时跳转登录页、Token 失效时清理本地状态、不展示无权操作入口。**前端不做任何安全判断**，即使绕过前端直接调用接口，也必须是安全的。

## 17. 金额计算规则

### 17.1 存储与类型

| 环节 | 规则 |
| --- | --- |
| 数据库 | `DECIMAL(10,2)`，范围 0.01 ~ 99,999,999.99 |
| Java 后端 | 一律使用 `java.math.BigDecimal`，**严禁使用 `float` / `double`** |
| 数据库读写 | 使用 `BigDecimal` 映射 `DECIMAL`，不经过 `double` 中转 |
| 接口传输 | 金额以**字符串**返回（如 `"31.00"`），避免 JSON 数字在客户端被解析为浮点数 |
| 前端 | 只展示；**不在前端做金额累加**，合计与占比一律取后端结果 |

### 17.2 计算规则

| 规则 | 说明 |
| --- | --- |
| 精度 | 统一 2 位小数，使用 `setScale(2, RoundingMode.HALF_UP)` |
| 符号 | 数据库中金额**恒为正数**，方向由 `type` 表达（收入 / 支出 / 不计收支） |
| 输入校验 | 金额 > 0；小数位 ≤ 2；不超过上限；不允许科学计数法 |
| 比较 | 使用 `compareTo`，禁止用 `equals` 比较金额（`1.0` 与 `1.00` 的 scale 不同会导致误判） |
| 求和 | 使用 SQL 的 `SUM(amount)`，返回 `BigDecimal`；空结果用 `IFNULL(SUM(amount), 0)` 保证不为 `null` |
| 结余 | `结余 = 月收入 - 月支出`，使用 `BigDecimal.subtract` |
| 除法 | 占比、使用率等除法统一保留 **1 位小数**，`RoundingMode.HALF_UP`；除数为 0 时直接返回 `0.0`，不做异常处理 |
| 解析外部数据 | 账单金额先清洗（去空格、制表符、货币符号、千分位逗号）再转 `BigDecimal`；转换失败计入解析失败 |

### 17.3 一个容易忽略的细节

账单里的金额字符串可能是 `¥2,000.00`、`49.74 `、`"20.00"`（带引号）甚至 `¥--`。清洗顺序必须是：

```text
去首尾空白与制表符
    → 去掉引号
    → 去掉 ¥ ￥ $ 等货币符号
    → 去掉千分位逗号
    → 校验是否为合法数字（正则 ^\d+(\.\d{1,2})?$）
    → new BigDecimal(...).setScale(2, HALF_UP)
```

任何一步失败都判定为"解析失败"，而不是用 `0` 兜底——**用 0 兜底会让用户账目悄悄出错**。

## 18. 统计计算规则

### 18.1 通用口径

1. 所有统计**只统计当前用户**的数据；
2. 所有统计**只统计 `type = 收入 / 支出`**，`NEUTRAL`（不计收支）一律排除；
3. 时间口径按 `bill_date`（DATE）比较，不涉及时分秒；
4. 服务器与数据库统一使用 `Asia/Shanghai` 时区；
5. 月份区间：`month = 2026-09` 对应 `2026-09-01` 至 `2026-09-30`；
6. 无数据时返回 `0.00`（而不是 `null`），前端不用做空值兜底。

### 18.2 月度统计

```text
月收入 = SUM(amount) WHERE type = 收入
月支出 = SUM(amount) WHERE type = 支出
月结余 = 月收入 - 月支出
```

示例输出：

```text
2026-09    收入 ¥1,500.00    支出 ¥1,286.50    结余 ¥213.50
```

### 18.3 分类统计

```sql
SELECT category, SUM(amount) AS total
FROM bill
WHERE user_id = ? AND type = 1 AND bill_date >= ? AND bill_date <= ?
GROUP BY category
ORDER BY total DESC;
```

占比如下计算（后端完成）：

```text
分类占比 = 分类金额 / 当月支出合计 × 100，保留 1 位小数
```

示例输出：

```text
餐饮  ¥486.00  37.8%
购物  ¥325.00  25.3%
交通  ¥126.00   9.8%
娱乐  ¥88.00    6.8%
其他  ¥261.50  20.3%
```

### 18.4 每日趋势

```sql
SELECT bill_date, SUM(amount) AS total
FROM bill
WHERE user_id = ? AND type = 1 AND bill_date >= ? AND bill_date <= ?
GROUP BY bill_date
ORDER BY bill_date;
```

规则：

- 返回**完整一个月的每一天**，没有消费的日期补 `0.00`（补零在后端完成，保证折线图连续）；
- 默认统计支出，可通过 `type` 参数切换为收入；
- 当月只统计到当月最后一天，不做未来日期填充以外的特殊处理。

### 18.5 来源统计

```sql
SELECT source, SUM(amount) AS total
FROM bill
WHERE user_id = ? AND type = 1 AND bill_date >= ? AND bill_date <= ?
GROUP BY source;
```

规则：

- 三种来源（`WECHAT`、`ALIPAY`、`MANUAL`）**始终返回**，无数据时为 `0.00`，避免前端缺项；
- 同时返回来源中文名（微信 / 支付宝 / 手动记录）与占比；
- 该统计只针对支出（"本月支出"下的来源构成），不混入收入。

### 18.6 首页概览

| 指标 | 计算方式 |
| --- | --- |
| 本月支出 | 见 18.2 |
| 本月收入 | 见 18.2 |
| 本月结余 | 见 18.2 |
| 今日花费 | 当天 `type = 支出` 的合计 |
| 最近记录 | 按 `bill_date DESC, id DESC` 取最近 5 条 |
| 预算剩余 | 见第 19 章 |

## 19. 预算计算规则

### 19.1 预算类型

| 类型 | 说明 | 存储方式 |
| --- | --- | --- |
| 月度总预算 | 一个用户一个月最多一条 | `budget.category = ''` |
| 分类限额 | 一个用户一个月内每个分类最多一条 | `budget.category = '餐饮'` 等 |

### 19.2 计算规则

```text
已使用 = 该月（该分类）支出合计（不含不计收支）
剩余   = 预算金额 - 已使用
使用率 = 已使用 / 预算金额 × 100，保留 1 位小数
超支   = 已使用 > 预算金额
```

规则细节：

- 预算金额必须 > 0，最多 2 位小数；
- **使用率不做上限截断**，超支时返回大于 100 的值（如 `128.5`），前端据此标红；
- 使用率 ≥ 80% 时前端显示"接近预算"提醒，超支时显示"已超支 ¥xx"；
- 未设置预算时，接口返回 `total = null`，前端提示"本月还未设置预算"并提供设置入口；
- 修改预算时按 `(user_id, month, category)` 唯一键做"存在则更新，不存在则插入"处理，避免同一月出现两条总预算；
- 预算的统计口径与第 18 章保持一致（排除不计收支），保证"预算已用"与"分类统计"数字对得上。

### 19.3 示例

```text
本月支出

¥1,286.50

微信       ¥586.50
支付宝     ¥700.00
手动记录   ¥0.00

本月预算  ¥2,000.00
已使用    ¥1,286.50（64.3%）
剩余      ¥713.50
```

## 22. 风险和限制

### 22.1 数据与格式风险

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 平台调整账单列名或列顺序 | 解析失败或解析错列 | 采用表头定位 + 列名映射；缺少关键列时明确报错；保留样例文件做回归测试 |
| 账单文件编码差异（GBK / UTF-8） | 中文乱码 | 编码探测（BOM → UTF-8 严格解码 → GB18030 兜底） |
| 用户误传商户版账单 | 无法解析 | 表头特征识别并给出明确提示，不尝试兜底 |
| 早期网页版导出的旧格式账单 | 不支持 | 明确提示"请重新导出用于个人对账的账单" |
| 压缩包加密 / 未解压直接上传 | 无法解析 | 前端提示先解压；后端对 zip 明确返回"请先解压后上传" |
| 单元格含制表符、空格、引号不一致 | 金额或单号解析错误 | 对所有单元格统一 trim 与清洗，并做格式校验 |

### 22.2 业务口径风险

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 转账、红包、提现、信用卡还款被当作真实收支 | 收支统计虚高 | 识别为"不计收支"，默认不勾选导入；统计时排除 |
| 退款如何记账 | 口径不一致 | 第一版按账单"收/支"字段处理（支付宝退款一般为"不计收支"），不做冲销计算，并在文档与界面说明 |
| 银行卡与支付宝同时产生一笔交易 | 重复记账 | 账单导入以平台流水为准；提示用户不要同时导入银行账单（第一版不支持银行账单） |
| 指纹去重的误判 | 少导入一条 | 已知局限，用户可手动补记 |
| 账单不提供真实消费分类（微信） | 分类不准 | 关键词匹配 + 用户预览时手动修改 |

### 22.3 环境与工程风险

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| **本机未安装 JDK / Maven** | 后端无法编译运行 | Stage 1 前安装 JDK 17 与 Maven 3.9+（需用户确认） |
| **本机未安装 Flutter SDK / Android SDK** | 前端无法运行 | 安装 Flutter SDK；或先以 Windows 桌面 / Chrome 为目标运行演示 |
| MySQL 已安装但账号密码未知 | 无法建库连接 | 使用现有 `MySQL80` 服务，新建专用数据库与账号（需用户提供或授权新建） |
| 前端金额展示精度 | 展示异常 | 金额以字符串传输，前端不做累加 |
| 演示环境无网络 / 无邮箱 | 现场无法导出真实账单 | 预先准备 `samples/` 下的样例账单文件，离线可演示 |

### 22.4 隐私与合规

| 要求 | 做法 |
| --- | --- |
| 不使用非官方接口 | 全部依赖用户自行导出的账单文件 |
| 不保存原始账单文件 | 内存解析，用完即丢，不落盘 |
| 不采集账单中的账号信息 | "对方账号"等字段在解析后丢弃，不入库 |
| 日志脱敏 | 不打印账单原始行、密码、完整 Token |
| 提示用户 | 导入页说明文件含个人信息，建议使用本人账号并自行删除邮件附件 |

### 22.5 明确的功能限制（第一版）

1. 不支持银行、信用卡、云闪付、微信/支付宝商户版账单；
2. 不支持加密压缩包与 `.xls` 旧格式；
3. 不做退款冲销与跨账户转账配对；
4. 不做多币种；
5. 不做后台管理与多人协作；
6. 不做 AI 分类。

## 23. 技术选型说明

### 23.1 选型与理由

| 层面 | 选型 | 理由 | 备选方案 |
| --- | --- | --- | --- |
| 后端框架 | Spring Boot 3.x | 国内课程设计主流，资料多、排错容易，天然支持 Web、JSON、文件上传、事务 | 无（需求已指定 Spring Boot） |
| 后端语言版本 | Java 17 | 长期支持版本，Spring Boot 3 的最低要求 | Java 21 |
| 持久层 | MyBatis-Plus | 单表 CRUD 与自定义统计 SQL 都很直观，符合课程设计习惯；分页插件开箱可用 | Spring Data JPA（抽象更多，复杂统计 SQL 反而更绕） |
| 数据库 | MySQL 8.0 | 真实关系型数据库，支持 `DECIMAL`、唯一约束、外键，本机已安装并运行 | SQLite（更省事，但需求明确要求真实数据库存储） |
| 认证 | JWT + BCrypt | 无状态、前后端分离友好、实现简单 | Session（在 Flutter 场景下更麻烦） |
| CSV 解析 | Apache Commons CSV | 正确处理引号、逗号与转义，避免手写 CSV 解析器的边界 bug | 手写解析器（不推荐，账单里有引号不统一的脏数据） |
| Excel 解析 | Apache POI | 支持 `.xlsx`，与 CSV 共用列名映射逻辑 | EasyExcel |
| 客户端 | Flutter 3.x | 需求指定；一套代码可跑 Android 与桌面，演示方便 | 无 |
| 状态管理 | Provider | 学习成本低、代码量小，适合学生项目 | Riverpod / Bloc（更重） |
| 图表 | fl_chart | 支持折线、柱状、饼图，社区活跃 | syncfusion_charts（体积与授权更复杂） |
| 文件选择 | file_picker | 可获取文件字节流，跨平台可用 | 平台原生实现 |

### 23.2 明确不采用的技术（避免过度设计）

| 不采用 | 原因 |
| --- | --- |
| 微服务 / 服务拆分 | 单体应用完全够用 |
| Redis / 缓存中间件 | 数据量小，无性能压力 |
| Kafka / RabbitMQ | 没有异步消息场景 |
| Elasticsearch | 账单检索用 SQL `LIKE` 足够 |
| Docker / 容器编排 | 课程设计不需要，且增加演示环境依赖 |
| CQRS / Event Sourcing / DDD 领域分层 | 过度设计，超出课程设计范围 |
| WebSocket | 无实时推送需求 |
| AI / RAG / 大模型分类 | 关键词匹配已满足需求 |
| 分布式事务 / 复杂工作流 | 无跨服务场景 |
| 大量自定义注解、泛型基类、抽象工厂 | 为抽象而抽象，增加阅读成本 |

### E.2 数据库最终实现

与第 11 章设计一致，交付时结构未再变动：`user`、`bill`、`budget`、`import_batch` 共 4 张表。

实现要点：

1. **分类不建表**：分类是固定集合（支出 10 类、收入 5 类、不计收支 5 类），用后端 `Category` 常量维护并校验，前端 `categories.dart` 保存同一份集合；
2. **金额一律 `DECIMAL(10,2)`**，后端 `BigDecimal`，接口以字符串传输，前端用整数分做展示级计算；
3. **去重靠数据库兜底**：`bill` 表唯一键 `(user_id, dedup_key)`，手动记账 `dedup_key` 为 NULL，因此不受去重约束；
4. **预算不重复**：`budget` 表唯一键 `(user_id, month, category)`，`category` 用空串表示月度总预算；
5. **索引都以 `user_id` 打头**，贴合"所有查询都带用户隔离"的特点；
6. **物理外键**保证引用完整性（删除用户级联清理其账单/预算/批次）。

### E.4 系统架构说明

| 层次 | 职责 |
| --- | --- |
| Controller | 接收参数、取当前登录用户（`CurrentUser.get()`）、调用 Service、包装统一响应；不含业务逻辑 |
| Service | 业务规则与校验（金额、日期、分类、预算）、事务边界、统计口径 |
| Mapper | MyBatis-Plus 单表操作 + 注解聚合 SQL（按类型/分类/日期/来源分组），全部带 `user_id` |
| Importer | 账单文件读取（编码探测、CSV/xlsx）、两个平台的解析器、导入编排（分类 → 去重 → 预览/入库） |
| Flutter | `pages`（页面）+ `services`（接口调用）+ `models`（模型）+ `widgets`（组件）+ `utils`（金额/日期/分类） |

两条关键链路：

```text
请求链路：Flutter → ApiClient（带 JWT）→ AuthInterceptor → Controller → Service → Mapper → MySQL
导入链路：选择文件 → 编码探测 → 表头定位 → 字段标准化 → 自动分类 → 去重检测 → 预览 → 用户确认 → 事务入库 + 记录批次
```

## 附录 H：Stage 3 智能记账与消费洞察

### H.1 设计原则

1. **可解释**：每条推荐与洞察都必须说明依据，禁止返回无法解释的结论；
2. **可测试**：算法抽成纯函数式的包级方法，单元测试直接验证打分与阈值；

### H.2 个性化分类推荐算法

候选分类来自用户自己的历史账单，按相似度打分：

| 匹配方式 | 分值 |
| --- | --- |
| 备注完全相同 | 120 |
| 商户名称完全相同 | 100 |

| 条件 | 加权 |
| --- | --- |
| 记录在最近 30 天内 | +15 |

## 附录 I：Stage 4-A 智能预算预测

> 本附录记录交付后追加的预算预测能力：在已有预算管理之上，按本月消费节奏推算月末支出并给出超支预警。
> 数据库结构未做任何改动，已有接口路径与预算 CRUD 语义均未变化。

### I.1 功能定位

预算管理原本只回答"已经花了多少"，本阶段补上"照这个速度，月底会花多少、会不会超支"。

设计原则：

1. **只用用户自己的数据**：全部输入是当前登录用户的 `bill`（账单）与 `budget`（预算）；
2. **不使用大模型、不调用外部服务**：算法是算术推算加阈值分级，没有黑盒；
3. **后端计算、前端展示**：金额、风险等级、中文说明都由后端算好，前端只负责颜色与排版；
4. **可解释**：每条预测都带一句把算式说全的中文说明，用户能自己复核算式；
5. **不新增表、不新增字段**：完全复用 `bill` 与 `budget` 的现有数据与索引。

### I.2 预测算法

```text
elapsedDays        = 当天的日号（不超过当月总天数）
dailyAverage       = 本月支出 ÷ elapsedDays            （两位小数，四舍五入）
projected          = dailyAverage × 当月天数
projectedOver      = max(projected − 预算, 0)
projectedUsageRate = projected ÷ 预算 × 100
overDate           = ceil(预算 ÷ dailyAverage) 对应的日期；超出当月范围则不返回
```

日均口径固定为「本月支出 ÷ 本月已过天数」，不掺入上月数据，理由是用户能用计算器自行验证。
代价是月初基数小、对突发大额敏感，由 I.4 的数据充分性闸门兜住。

**可解释性**：每条预测附带 `message`，形如
「本月已过 17 天，已支出 ¥500.00，日均 ¥29.41；按此推算月末约支出 ¥882.30，为预算的 147.05%，预计超出预算 ¥282.30」。

### I.3 风险等级

风险按**预测使用率**分级，而不是当前已用比例——月初花掉一半并不代表一定超支，
推算到月底才是有意义的预警信号。

| 预测使用率 | 等级 | 前端文案 | 前端颜色 |
| --- | --- | --- | --- |
| < 60% | `SAFE` | 安全 | 绿色 |
| 60% ~ 85% | `LOW` | 留意 | 浅绿 |
| 85% ~ 100% | `MEDIUM` | 接近预算 | 品牌橙 |
| 100% ~ 120% | `HIGH` | 预计超支 | 橙红 |
| ≥ 120% | `OVER` | 严重超支 | 品牌红 |

后端只返回等级字符串，颜色与图标属于 UI 层，由 Flutter 映射。

### I.4 数据充分性与状态

**数据充分性闸门**：当月有支出的天数少于 3 天时不给预测结论。
理由：月初只花过一两笔时，日均会被极度放大（例如 9 月 2 日花了 500 元会推出月末 7500 元），
这种"算法正确但业务错误"的预警对用户是噪音。3 天是能区分"偶发一两笔"与"真实消费节奏"的最小样本。

**每个预算各自判断样本**：总预算用当月整体消费天数，分类预算用该分类自己的消费天数。
否则「娱乐预算本月一次都没花过」会因为别的分类花过钱而被判定为样本充足，从而产出一条基于日均 0 的错误预测。

| status | 触发条件 | items 内容 |
| --- | --- | --- |
| `OK` | 当前月 + 有预算 + 至少一条预算样本充足 | 全部预算条目（含预测结论） |
| `INSUFFICIENT_DATA` | 当前月 + 有预算，但所有条目样本都不足 | 仍返回条目，但预测字段为 0、`overDate` 为 null、`riskLevel` 为 `INSUFFICIENT_DATA`，`message` 只陈述「已使用 x / 预算 y」 |
| `NO_BUDGET` | 当前月没有设置任何预算 | 空列表，且不再查询账单 |
| `NOT_APPLICABLE` | 传入月份不是当前月（过去或未来） | 空列表 |

### I.5 接口

```text

鉴权：JWT（走已有 AuthInterceptor，未登录返回 401）
```

## 附录 J：Stage 4-B 智能周期性账单识别

> 本附录记录交付后追加的周期性支出识别能力：从用户历史账单中找出会重复发生的消费。
> 数据库结构未做任何改动，已有接口路径与账单业务逻辑均未变化。

### J.1 功能定位

预算预测回答「按这个速度月底会不会超支」，消费洞察回答「这个月发生了什么」，
周期识别回答的是**「哪些消费可能会周期性再次发生」**——它是项目里唯一跨月、面向未来的模式识别能力。

典型场景：每月自动续费的视频会员、每月固定的话费与校园网、每周固定的通勤支出。

### J.2 设计原则

1. **只基于用户自身账单数据**：全部输入是当前登录用户的 `bill` 记录；
2. **不调用外部服务、不使用大模型**：算法是间隔统计加阈值判断，没有黑盒；
3. **后端实时计算、前端展示结果**：识别结果不落库，每次请求按当前账单重新计算；
4. **只读分析、不修改账单**：识别过程不写任何数据；
5. **可解释**：每条结果都带周期类型、样本数、间隔区间、平均金额与一句可复核的中文说明；
6. **不新增表、字段、索引**：完全基于已有的 `bill` 数据。

### J.3 数据来源

唯一数据源是 `bill` 表，查询条件是**当前登录用户 + 支出类型 + 最近 180 天 + 商户非空**。

商户为空的记录（手动记账时商户是选填项）没有分组依据，直接跳过。

### J.4 算法设计

```text
1. 一次范围查询取最近 180 天的支出明细（商户非空，LIMIT 2000）
2. 商户归一化后分组
3. 样本过滤：少于 4 次的分组跳过；平均间隔小于 5 天的分组跳过（高频过滤）
4. 周期判断：按日期升序算相邻间隔，取中位数匹配周期区间，
   同时要求区间覆盖率 ≥ 60%
5. 信号评分：四项信号计数
6. 置信度输出：4 个信号 = HIGH，3 个 = MEDIUM，≤ 2 个不返回
7. 输出排序：置信度优先，其次样本数
```

**商户归一化规则**（保持简单、可解释，不做模糊匹配）：

```text
1. trim
2. 去除半角与全角空格
3. 统一转小写（大小写不敏感）
4. 剥离明确的长后缀：有限责任公司 / 有限公司 / 专卖店 / 旗舰店 / 分店 / 门店
```

**刻意不剥离单独的「店」字**：酒店、便利店、药店等名称里的「店」是名称本身的一部分，
剥掉会把「如家酒店」变成「如家酒」，造成错误合并。长后缀按长度从长到短匹配，
避免「有限责任公司」被「有限公司」先截断。

### J.5 周期判断

| 周期 | 目标间隔 | 容许区间 | 说明 |
| --- | --- | --- | --- |
| `WEEKLY` | 7 天 | **5 ~ 10 天** | 覆盖「周四→下周三」（6 天）与「周五→下周日」（9 天）这类抖动 |
| `BIWEEKLY` | 14 天 | **12 ~ 17 天** | 与 WEEKLY 区间不重叠 |
| `MONTHLY` | 30 天 | **26 ~ 35 天** | 覆盖 2 月（28 天）到 31 天月份的真实间隔 |

三个区间互不重叠，一组数据只能落进一个周期。

**为什么用中位数而不是平均间隔**：平均间隔容易被一次漏记带偏（例如某月漏缴导致一次 60 天间隔），
中位数不受影响。但只靠中位数不够——间隔完全杂乱时中位数也可能偶然落进区间
（例如间隔为 2/3/9/15/22/30/40 天时中位数是 15，恰好在双周区间内），
因此额外要求**区间覆盖率 ≥ 60%**，否则不匹配任何周期。

**不支持 `DAILY` 与 `QUARTERLY`**：每日消费（食堂、公交、奶茶）满足周期定义但不符合用户认知；
季度周期在 180 天窗口内最多观察 2 次，达不到样本门槛。

### J.6 四信号模型

每条候选计算四个布尔信号：

| 信号 | 通过条件 |
| --- | --- |
| 间隔稳定 | **每一次**相邻间隔都落在该周期的容许区间内 |
| 金额稳定 | 变异系数 `CV ≤ 0.15`（CV = 标准差 ÷ 平均金额） |
| 商户一致 | 归一化后商户名完全相同（分组前提，恒为真） |
| 分类一致 | 主导分类占该商户全部记录的比例 `≥ 80%` |

**分类信号的一个实现要点**：分类不一致时，若主导分类的记录本身 ≥ 4 条，则收窄到该子集计算
周期与金额稳定性；否则回退到全部记录（此时金额波动会体现真实情况）。
但**分类信号始终按原始分组的比例判定**，不按收窄后的子集重算——
否则 71% 一致的分组会因为子集变成 100% 而重新拿到 HIGH。

**高频过滤**：平均间隔小于 5 天的分组直接排除。这条规则不可省略——
实测中「每天固定 6 元的校园班车」在金额与间隔上都完美稳定，若没有频率上限会被判为 WEEKLY/HIGH，
成为典型误报。

### J.7 置信度模型

| 通过信号数 | 置信度 | 前端中文 | 是否返回 |
| --- | --- | --- | --- |
| 4 | `HIGH` | 高可信 | 返回 |
| 3 | `MEDIUM` | 中可信 | 返回 |
| ≤ 2 | — | — | **不返回** |

不输出低可信结论：信号 ≤ 2 意味着至少两个维度不成立（例如间隔稳但金额乱），
误报概率过高，与其输出可疑推荐不如不输出——与 Stage 3 分类推荐「NONE 不显示虚假推荐」的原则一致。

| --- | --- |

## 附录 K：Stage 4-C 智能消费异常检测

> 本附录记录 Stage 4-C 的最终实现，格式与附录 E~J 一致：只描述"实现是什么样"，
> 不改动前面章节的设计基线，也不回改附录 E~J 中的历史测试数字。

### K.1 阶段目标

回答一个问题：**指定月份里，哪些消费偏离了用户自己的常态？**

Stage 3 的消费洞察里原本有一条 `BIG_EXPENSE` 规则，用来提示"本月有一笔大额消费"。
它能跑通，但存在三个结构性问题：

| 问题 | 具体表现 |
| --- | --- |
| 基线不对 | 用**全局**平均单笔金额做基线，不区分分类。一笔 300 元的聚餐放在日均 15 元的餐饮里不算异常，放在日均 3 元的交通里才算，旧规则却给出同一个判断 |
| 窗口太短 | 只看近 30 天，月初时窗口里可能只有上月末的几笔，基线抖动大 |
| 容量太小 | 每月最多输出 1 条，一个月里出现两笔明显异常时只能看到其中一条 |

Stage 4-C 因此把单笔异常从 `InsightsService` 里**整体迁移**出来，
升级为独立的三类异常检测，并把 `BIG_EXPENSE` 从 `monthly()` 中彻底移除，避免同一件事被提醒两次。

**职责分离**是本阶段的核心设计决定：

| 维度 | 月度消费洞察 `InsightsService` | 消费异常检测 `SpendingAnomalyService` |
| --- | --- | --- |
| 回答的问题 | 这个月的**结构**是什么样（占比、环比、预算） | 这个月哪里**偏离了常态** |
| 对比对象 | 本月 vs 上一个月 | 本月 vs 前 3 个月基线（分类自己的基线） |
| 输出上限 | 最多 5 条 | 最多 5 条 |
| 是否用中位数 | 否 | 是（单笔异常） |
| 数据来源 | 已有统计结果 | 两次针对性聚合查询 |

两者都输出"最多 5 条"，但**规则不共享**：洞察的结构性结论（占比、环比）不应该被异常检测的阈值污染，
异常检测的绝对差额门槛也不应该影响洞察的口径。因此不合并成一个 Service。

### K.2 架构

```text
InsightsController                （@RequestMapping("/api/insights")）
        │
        ├── GET /monthly    → InsightsService          月度结构性洞察
        ├── GET /recurring  → RecurringBillService     Stage 4-B 周期识别
        └── GET /anomalies  → SpendingAnomalyService   Stage 4-C 异常检测

SpendingAnomalyService
        ├── CATEGORY_SPIKE       分类月度上涨
        ├── LARGE_TRANSACTION    单笔异常消费（替代原 BIG_EXPENSE）
        └── FREQUENCY_SPIKE      消费频次异常
                │
                └── BillMapper
                        ├── sumByCategoryAndMonth   一次拿到目标月 + 前 3 个月的分类聚合
                        └── selectExpenseDetails    一次拿到目标月前 90 天 + 目标月的支出明细
```

分层仍遵守项目既有约定：

- `Controller` 只做「取当前用户 → 调用 Service → 包装统一响应」，**没有任何算法代码**；
- `Service` 负责取数、基线计算、阈值判定、排序与文案生成；
- `Mapper` 只提供带 `user_id` 条件的查询；异常检测的两个查询是新增方法，不改动既有查询。

### K.3 BIG_EXPENSE 迁移

| 项 | 旧实现（Stage 3 `InsightsService.BIG_EXPENSE`） | 新实现（Stage 4-C `LARGE_TRANSACTION`） |
| --- | --- | --- |
| 基线 | 近 30 天**全局**平均单笔金额 | 目标月**开始之前** 90 天**同分类**单笔金额中位数 |
| 触发 | `amount ≥ 平均 × 3` | `amount ≥ median × 3` 且 `amount − median ≥ ¥100` |
| 样本门槛 | ≥ 3 笔 | ≥ 5 笔 |
| 严重度 | 无分级 | HIGH（`≥ median × 5`）/ MEDIUM（`≥ median × 3`） |
| 输出上限 | 每月最多 1 条 | 与其他异常共同占用最多 5 条 |
| 定位信息 | 无 | 返回 `merchant` 与 `billDate`（商户为空时回退为分类） |

**迁移原因**：

1. 用分类自己的基线替代全局平均，消除不同消费类别之间的量级干扰；
2. 用中位数替代平均数，避免单笔极端值把基线本身抬高；
3. 窗口从 30 天扩到 90 天，让基线覆盖约 3 个月的消费节奏；
4. 允许一个月里同时输出多条异常，并给出可解释的倍数与差额。

**迁移动作**：`InsightsService` 中删除 `BIG_EXPENSE_MULTIPLIER`、`AVERAGE_WINDOW_DAYS`、
`AVERAGE_SAMPLE_LIMIT`、`addBigExpenseInsight()` 以及 `monthly()` 中对应的调用；
`dto/Insight.java` 中关于 `BIG_EXPENSE` 的注释同步删除。
从此 **`monthly()` 不再输出任何单笔异常**，单笔异常只由 `/api/insights/anomalies` 返回，
两个接口之间不存在重复提醒。对应的两个旧单元测试被删除，其余 `InsightsService` 行为保持不变。

### K.4 三类异常算法

阈值常量集中在 `SpendingAnomalyService` 顶部，每个常量都带中文注释说明取值理由。

#### 公共约定

| 项 | 值 | 说明 |
| --- | --- | --- |
| 基线月数 `BASELINE_MONTHS` | 3 | 目标月之前的 3 个完整自然月 |
| 缺月处理 | 只对**有消费的月份**取平均 | 把没有记录的月份按 0 计入会拉低基线，让一笔正常支出被误判为暴涨 |
| 绝对差额门槛 `MIN_ABSOLUTE_DELTA` | ¥100 | 只有倍数门槛会产生噪声：日均 ¥12 的通讯涨到 ¥20 是 67% 涨幅，但只多了 ¥8，提醒没有价值 |
| 条数上限 `MAX_ITEMS` | 5 | 与消费洞察保持一致，避免页面堆满文字 |
| 明细上限 `MAX_DETAIL_ROWS` | 2000 | 兜住极端高频用户 |
| 统计范围 | 只看 `type = 1`（支出） | 收入与不计收支都不参与 |

#### 1. CATEGORY_SPIKE（分类月度上涨）

数据来源：`sumByCategoryAndMonth`（目标月 + 前 3 个月的分类聚合）。

```text
baseline = 前 3 个自然月中「有消费月份」的金额平均值

触发：baseline > 0
      current ≥ baseline × 1.5        （CATEGORY_SPIKE_RATIO）
      current − baseline ≥ ¥100       （MIN_ABSOLUTE_DELTA）

严重度：HIGH    current ≥ baseline × 2.5   （CATEGORY_SPIKE_HIGH_RATIO）
        MEDIUM  current ≥ baseline × 1.5
```

页面文案示例：`餐饮本月 ¥1200.00，前 3 个月平均 ¥400.00，上涨 200.00%（多支出 ¥800.00）`。

#### 2. LARGE_TRANSACTION（单笔异常消费）

数据来源：`selectExpenseDetails`（目标月开始前 90 天 ~ 目标月月末的支出明细）。

**基线窗口边界（关键设计点）**：

```text
基线窗口 = 目标月开始之前 90 天
目标月账单只负责检测，不参与自己的基线计算
```

如果把目标月的账单混进基线，一笔异常大额会把中位数明显抬高，导致它自己达不到 3 倍门槛而**漏报**。
实现上取数范围是「目标月开始前 90 天 ~ 目标月月末」，
随后在内存里按 `bill_date < 目标月 1 日` 切出基线明细、按 `YearMonth = 目标月` 切出待检测明细。
**注意不要把它描述成"目标月末往前 90 天"**，那是错误口径。

```text
样本：同分类基线明细 ≥ 5 笔        （MIN_CATEGORY_SAMPLES）
基线：这些明细金额的中位数          （偶数个取中间两个的平均）

触发：median > 0
      amount ≥ median × 3          （TRANSACTION_RATIO）
      amount − median ≥ ¥100

严重度：HIGH    amount ≥ median × 5 （TRANSACTION_HIGH_RATIO）
        MEDIUM  amount ≥ median × 3
```

定位信息：`merchant` 优先；商户为空或全是空格时回退为分类名（`merchant → category`），
**不会因为商户为空而丢弃这条异常**。`billDate` 始终返回。

页面文案示例：`数码店 2026-09-10 支出 ¥300.00，该分类近 90 天单笔中位数 ¥20.00，约为 15.00 倍`。

#### 3. FREQUENCY_SPIKE（消费频次异常）

数据来源：与 CATEGORY_SPIKE 同一份聚合结果（复用 `count` 列，不额外查询）。

```text
baselineCount = 前 3 个自然月中「有消费月份」的平均笔数

触发：baselineCount ≥ 2                       （MIN_BASELINE_COUNT）
      currentCount ≥ baselineCount × 2        （FREQUENCY_SPIKE_RATIO）
      currentCount − baselineCount ≥ 5        （FREQUENCY_SPIKE_MIN_DELTA）

严重度：HIGH    currentCount ≥ baselineCount × 3 （FREQUENCY_SPIKE_HIGH_RATIO）
        MEDIUM  currentCount ≥ baselineCount × 2
```

`baselineCount ≥ 2` 是"常态下限"：一个月本来只买 1 次的东西，这个月买 2 次不构成频次异常。

页面文案示例：`交通本月 8 笔，前 3 个月平均 3.00 笔，多 5.00 笔`。

#### 排序与截断

```text
排序：严重度降序（HIGH 先） → 差额降序 → 分类字典序
截断：取前 MAX_ITEMS（5）条
```

差额用 `difference` 字段的数值比较（频次异常的差额是笔数）。
三类规则可能同时命中同一分类（例如某分类既金额上涨又频次翻倍），
此时两条都会保留，因为它们解释的是不同维度的问题。

#### 状态判定

状态只基于这两次查询的结果判定，不额外增加 SQL：

| status | 判定条件 | message |
| --- | --- | --- |
| `NO_DATA` | 目标月在 4 个月窗口内没有任何分类聚合 | 本月还没有支出记录 |
| `NOT_ENOUGH_BASELINE` | 目标月有支出，但窗口内只有目标月这一个月有数据 | 积累几个月数据后，这里可以对比出消费异常 |
| `NO_ANOMALY` | 基线可用，但三类规则都没有命中 | 本月消费节奏正常，没有发现明显异常 |
| `OK` | 命中至少 1 条 | 本月发现 N 处消费异常 |

### K.5 API

```text

```

| 项 | 说明 |
| --- | --- |
| 鉴权 | 复用项目既有 `AuthInterceptor` + JWT（`/api/**` 默认拦截），未登录返回 401 |

### K.6 数据库与查询

**数据库无任何结构变化**：仍为 4 张表（`user` / `bill` / `budget` / `import_batch`）；
索引结构与数量完全未变——实测 `information_schema.statistics` 共 13 个索引对象
（`bill` 表 7 个，`user` / `import_batch` / `budget` 各 2 个，均含主键），
没有新增表、字段或索引，也没有数据迁移。

新增两个 Mapper 查询方法（都带 `user_id` 与 `type = 支出` 条件）：

| 方法 | 作用 | 范围 |
| --- | --- | --- |
| `sumByCategoryAndMonth` | 分类 × 月份的金额与笔数聚合 | 目标月前 3 个月的 1 日 ~ 目标月月末 |
| `selectExpenseDetails` | 支出明细（分类、金额、日期、商户） | 目标月开始前 90 天 ~ 目标月月末，`LIMIT 2000` |

**查询次数固定为 2 次**：

```text
detect(userId, month)
        ├── 查询 1：sumByCategoryAndMonth   → 分类/频次基线 + 本月取值
        └── 查询 2：selectExpenseDetails    → 单笔异常的中位数基线 + 本月明细
```

分类维度不做循环查询（**禁止 N+1**）：中位数无法用 SQL 聚合直接算出，
因此一次取回全部明细后在内存里分组排序计算，而不是「for 分类 → 查一次数据库」。
`NO_DATA` 与 `NOT_ENOUGH_BASELINE` 会在查询 1 之后提前返回，此时只发生 1 次查询。

## 附录 L：Stage 4-D 智能下月支出预估

> 本附录记录 Stage 4-D 的最终实现，格式与附录 E~K 一致：只描述"实现是什么样"，
> 不改动前面章节的设计基线，也不回改附录 E~K 中的历史测试数字。

### L.1 功能目标

回答一个问题：**照我过去的消费节奏，下个月大概会花多少？**

它**不依赖任何预算**：只要用户有历史消费记录就能给出预估，没有设置预算也能正常使用。

与 Stage 4-A「智能预算预测」的分工（两者互不重复，可以同时存在）：

| 维度 | Stage 4-A 智能预算预测 | Stage 4-D 智能下月支出预估 |
| --- | --- | --- |
| 回答的问题 | 这个月会不会超出预算 | 下个月大概要花多少钱 |
| 时间方向 | 本月 → 本月月末 | 本月 → 下个月 |
| 是否依赖预算 | **依赖**（无预算时返回 `NO_BUDGET`，不给结论） | **不依赖**（只读历史账单） |
| 计算方式 | 本月已支出 ÷ 本月已过天数 × 当月总天数 | 最近 3 个有效完整自然月按 3 : 2 : 1 加权 |
| 结果粒度 | 每个预算一条（是否超支、预计超支金额、触顶日期） | 一条总量预估 + 置信度 + 样本依据 |

设计上刻意**不做"本月预估"**：那正是 4-A 已经在做的事，重复实现会让同一个页面上出现两个含义相近的"预计"。

### L.2 架构设计

```text
Backend
├── controller/InsightsController           新增 GET /forecast（第 4 个洞察接口）
├── service/SpendingForecastService         取数 + 选样 + 加权 + 置信度 + 文案
├── dto/SpendingForecastResponse            响应体（14 个字段）
└── dto/ForecastSampleMonth                 样本明细（month / amount / weight）

Frontend
├── models/spending_forecast.dart           数据解析（防御式，未知字段忽略）
├── widgets/forecast_card.dart              ForecastCard + ForecastSection
├── services/insight_service.dart           扩展 forecast(month)（不新建 Service）
└── pages/statistics_page.dart              独立 try/catch + 插入区块
```

分层遵守项目既有约定：`Controller` 只做「取当前用户 → 调 Service → 包统一响应」，
`Service` 负责全部算法与文案，`Mapper` 只提供带 `user_id` 的查询。

### L.3 数据流程

```text

        ↓  InsightService.forecast(month)

        ↓  CurrentUser.get() 取得 userId

        ↓  一次查询覆盖「参考月前 6 个完整自然月 + 参考月」

        ↓
SpendingForecastResponse（金额 + 对比 + 置信度 + 样本依据）
        ↓
ForecastSection / ForecastCard 展示
```

```text

读取窗口内没有任何支出                → NO_DATA（1 次查询）
有支出但有效完整月 < 3                → INSUFFICIENT_DATA（1 次查询）
有效完整月 ≥ 3                        → OK（1 次查询）
```

### L.4 算法设计

**有效月份**：该自然月的支出合计 **> 0**。
没有支出的月份**不按 ¥0 计入**（否则会把预估拉低），直接在选样时跳过，并向后顺延到更早的月份。

**样本**：最近 3 个有效完整自然月，按时间倒序取权重。

```text
权重：最近月 ×3、次近月 ×2、第三近月 ×1
预测金额 = (m1 × 3 + m2 × 2 + m3 × 1) / 6      （四舍五入到分）
```

示例：2026-08 ¥1250、2026-07 ¥1180、2026-06 ¥1320

```text
(1250×3 + 1180×2 + 1320×1) / 6 = 7430 / 6 = ¥1238.33
```

**当前月不参与**：即使参考月已经记录了大量账单，它也只作为"本月已支出"的事实展示，不进入样本。

**异常月处理**：

```text
med = 3 个样本金额的中位数
若某月 amount > med × 2 → 视为异常月，该月权重由 3（或 2）降为 1，并记录到置信度依据中
```

例：2026-08 ¥8500、07 ¥1200、06 ¥1100 → 中位数 1200、阈值 2400，08 为异常月
→ 权重变为 `1 / 2 / 1` → `(8500×1 + 1200×2 + 1100×1) / 4 = ¥3000.00`。

异常月**不剔除**（保留信息），只是降低它对结果的影响；同时置信度不得高于 `MEDIUM`。
本模块**不调用 Stage 4-C 的异常检测**（4-C 判的是分类级与单笔级异常，4-D 需要的是"某个月"整体是否偏离），
异常月判定只是内存里对 3 个数字做一次中位数比较，零额外查询。

**与最近有效月份的对比**：

```text
previousMonthAmount    = 样本中最近的那个有效月份的实际支出
predictedDifference    = predictedAmount − previousMonthAmount
predictedChangePercent = (predictedAmount − previousMonthAmount) ÷ previousMonthAmount × 100
                         （分母为 0 时不生成，返回 null）
```

### L.5 置信度

置信度**只由客观条件决定**：样本月份之间的波动幅度，以及是否存在异常月。

```text
极差比 = (样本最高月金额 − 样本最低月金额) ÷ 预估值
```

| 置信度 | 条件 |
| --- | --- |
| `HIGH` | 极差比 ≤ 0.30，且不存在异常月 |
| `MEDIUM` | 极差比 ≤ 0.60，或存在异常月（封顶） |
| `LOW` | 极差比 > 0.60 |

阈值 0.30 / 0.60 的含义：3 个月样本里最高与最低相差不超过 30% 可认为消费节奏稳定；
超过 60% 说明月份之间几乎没有可比性，只能"仅供参考"。

后端同时返回 `confidenceReason`，用客观数字说明依据，例如：

```text
近 3 个月最高 ¥1320.00、最低 ¥1180.00，相差 11.31%
近 3 个月最高 ¥8500.00、最低 ¥1100.00，相差 246.67%；2026-08 明显高于其他月份（超过中位数的 2 倍），已降低其权重
```

前端按 `confidence` 做展示层映射（后端不返回颜色与展示文案）：
`HIGH → 较稳定`、`MEDIUM → 一般`、`LOW → 波动较大`，未知取值回退到后端 `confidenceLabel`。

### L.6 API

```text
GET /api/insights/forecast?month=yyyy-MM
```

| 项 | 说明 |
| --- | --- |
| 鉴权 | 复用既有 `AuthInterceptor` + JWT，未登录 401 |
| 用户隔离 | `userId` 只来自 `CurrentUser.get()`，方法签名不接受 `userId`，前端也无法通过参数改变数据归属 |
| 参数 | `month`（参考月）必填，格式 `yyyy-MM`；空值 / 格式错误 → 400（复用 `Months.parse`） |
| 范围 | 仅「参考月 = 服务器当前月」给出预估；过去与未来月份返回 `NOT_APPLICABLE`（HTTP 200，不是错误） |

响应结构：

```text
SpendingForecastResponse
├── month                    参考月（yyyy-MM）
├── targetMonth              被预估的月份（参考月 + 1）
├── status                   OK / INSUFFICIENT_DATA / NO_DATA / NOT_APPLICABLE
├── message                  中文说明
├── confidence               HIGH / MEDIUM / LOW（非 OK 时为 NONE）
├── confidenceLabel          后端文案（展示层按 confidence 映射）
├── confidenceReason         置信度的客观依据（非 OK 时为空串）
├── predictedAmount          预估金额（非 OK 时为 "0.00"）
├── previousMonthAmount      最近一个有效月份的实际支出
├── predictedDifference      与最近有效月份的差额（非 OK 时为 null）
├── predictedChangePercent   变化率（无法比较时为 null）
├── currentMonthAmount       参考月至今实际支出（事实陈述）
├── elapsedDays              参考月已过天数
└── sampleMonths             参与加权的月份 [{month, amount, weight}]（最多 3 条，时间倒序）
```

状态的判定条件与页面表现：

| status | 判定条件 | 页面表现 |
| --- | --- | --- |
| `OK` | 有效完整月 ≥ 3 | 预估卡片（金额 + 对比 + 置信度 + 依据 + 免责说明） |
| `INSUFFICIENT_DATA` | 有支出历史，但有效完整月 < 3 | 「目前历史数据不足，继续记录几个月后可以预测」+ 本月已支出事实 |
| `NO_DATA` | 读取窗口内没有任何支出 | 「本月暂无支出记录，记录几笔账单后即可预估」 |
| `NOT_APPLICABLE` | 参考月不是当前月 | 「该月份不支持预测」 |

### L.10 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| 1 | **数据不足时不给预测** | 有效完整月少于 3 个时返回 `INSUFFICIENT_DATA`，只展示引导与本月事实，不编造数字 |
| 2 | **只预测总支出** | 不拆分到分类：单个分类的月度样本更稀疏（医疗、学习等可能几个月才出现一次），噪声远大于总额 |
| 3 | **不预测未来 7 天** | 需要更强的"周内季节性"，个人记账数据密度不足以支撑；且与 4-A 的本月外推数值高度重叠 |
| 4 | **不使用机器学习模型** | 现实数据只有 3~7 个月，ARIMA / Prophet / LSTM 之类模型在如此短的序列上等于过拟合，还会破坏单体架构与可解释性 |
| 5 | **历史跨度有限** | 只读取参考月之前 6 个完整自然月；更早的数据不参与，也无法预测两个月以后的月份 |
| 6 | **用户最早的那个月可能不完整** | 月中开始记账的用户，其首个有支出的月份会被当作完整月参与加权，可能略微低估；样本少时置信度会自动下降 |
| 7 | **异常月降权后仍占 25% 权重** | 权重降为 1 后（`1 / 2 / 1`）异常月仍占 1/4 权重，只是不再主导结果；这是"保留信息"与"抑制影响"之间的折中 |
| 8 | **没有人工截图的视觉确认** | 受执行环境限制（浏览器自动化不可用），前端渲染正确性由「真实后端数据 + Widget 渲染断言」覆盖 |

### P.3 缺陷与修复（真机阻塞级）

**现象**：在手机上输入正确的账号密码后，点击登录没有任何反应（无报错提示、无跳转）；
同时后端日志里**一条请求都没有**，说明请求根本没有离开手机。

**排查过程**：

1. 先看后端：10 分钟 0 条 SQL → 排除"密码错误"；
2. 再解包 APK 检查烧进去的接口地址（`libapp.so` 中的字符串）→ 确认为 `8.138.161.154`，排除"打包时用了 localhost"；
3. 在手机里执行 `curl http://8.138.161.154:8090/api/health` → 返回正常 JSON，排除"网络不通"；
4. 检查已安装应用的权限清单（`adb shell dumpsys package`）→ **`requested permissions` 中只有一条 `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`，没有 `android.permission.INTERNET`**。

**根因**：Flutter 的 Android 模板把 `<uses-permission android:name="android.permission.INTERNET"/>`
只放在 `android/app/src/debug/AndroidManifest.xml` 与 `profile/AndroidManifest.xml` 中，
`main/AndroidManifest.xml` 里没有声明它。因此：

- `flutter run`（debug）与 `flutter build web` 都能联网，问题被掩盖；
- **release 包无法发起任何 HTTP 请求**，所有依赖后端的界面都会"点了没反应"。

**修复**：在 `frontend/android/app/src/main/AndroidManifest.xml` 的 `<manifest>` 下补上该权限声明
（并加注释说明原因），然后重新打包安装。

**验证**：

| 检查 | 结果 |
| --- | --- |
| 应用权限 | `android.permission.INTERNET: granted=true` |
| 真机登录 | 成功进入首页，显示线上真实数据 |
| 后端口径 | 同一时间窗 SQL 由 0 条变为 76 条 |
| 页面一致性 | 首页 / 统计页金额与接口返回逐字一致 |

## 附录 O：Stage 4-G 智能收支结余分析

> 本附录记录 Stage 4-G 的最终实现，格式与附录 E~N 一致：只描述"实现是什么样"，
> 不改动前面章节的设计基线，也不回改附录 E~N 中的历史测试数字。

### O.1 功能目标

回答一个问题：**我这个月存下了多少？**

这是系统里**唯一分析收入侧**的能力。在它之前，Stage 4-A ~ 4-F 六个智能模块全部只看支出
（预算风险、周期、异常、下月总量、时间分布、消费对象），"收入够不够花"始终没有答案。

| 模块 | 回答的问题 | 分析侧 |
| --- | --- | --- |
| 4-A ~ 4-F | 预算 / 周期 / 异常 / 下月总量 / 时间分布 / 消费对象 | 全部是支出侧 |
| **4-G 收支结余分析** | **这个月存下了多少** | **收入 − 支出** |

### O.2 与既有能力的边界

| 对比对象 | 4-G 与它的区别 |
| --- | --- |
| 统计接口「月度概览」 | 只给出收入 / 支出 / 结余三个原始数字；4-G 在此基础上给出**结余率、收入结构、与上月对比与一句话结论** |
| 4-A 智能预算预测 | 4-A 比较"支出 vs 预算"（依赖预算）；4-G 比较"支出 vs 收入"（不依赖任何配置） |
| 4-D 智能下月支出预估 | 4-D 预测未来支出总量；4-G 只描述当月已发生的收支结果，不做任何预测 |

```text
├── dto/IncomeBalanceResponse          响应体（13 个字段）
└── dto/IncomeCategoryItem             收入结构项（category / amount / count / percentage）
```

### O.4 数据流程

```text
统计页（选中月份） → InsightService.balance(month)
        ↓
InsightsController  GET /api/insights/balance?month=yyyy-MM
        ↓  CurrentUser.get() 取得 userId
IncomeBalanceService.analyze(userId, month)
        ↓  参考月 ≠ 当前月 → NOT_APPLICABLE（0 次查询）
        ├─ 查询 1：BillMapper.sumByType(本月)                 → 收入 / 支出合计
        ├─ 查询 2：BillMapper.sumByCategoryAndMonth(type=收入) → 收入结构
        └─ 查询 3：BillMapper.sumByType(上月)                 → 与上月对比（仅 OK 路径）
        ↓
IncomeBalanceResponse → BalanceSection / BalanceCard 展示
```

状态判定顺序：非当前月 → `NOT_APPLICABLE`（0 次查询）；收支都为 0 → `NO_DATA`（1 次查询）；
有支出但收入为 0 → `NO_INCOME_DATA`（2 次查询）；否则 → `OK`（3 次查询）。

### O.5 算法设计

```text
balance       = income − expense                  （可能为负，代表超支）
balanceRate   = balance ÷ income × 100            （income = 0 时返回 0.00，不编造）
收入结构占比    = 该分类收入 ÷ 当月总收入 × 100
balanceChange = 本月结余 − 上月结余                （上月无记录时为 null，不展示对比）
```

只统计 `type=1`（支出）与 `type=2`（收入）；`type=3`（不计收支）完全不参与；
收入结构按金额降序、最多 5 项；收入笔数由各分类笔数合计。

### O.6 API 设计

```text
GET /api/insights/balance?month=yyyy-MM
```

| 项 | 说明 |
| --- | --- |
| 鉴权 | 复用 `AuthInterceptor` + JWT，未登录 401 |
| 用户隔离 | `userId` 只来自 `CurrentUser.get()`，方法签名不接受 `userId` |
| 参数 | `month`（参考月）必填，格式 `yyyy-MM`；空值 / `2026-9` / `abc` → 400 |
| 范围 | 只分析目标月本身；非当前月份返回 `NOT_APPLICABLE`（HTTP 200，不是错误） |

响应字段：`month` / `status` / `message` / `incomeAmount` / `expenseAmount` / `balance` /
`balanceRate` / `incomeCount` / `incomeItems[]` / `previousBalance` / `balanceChange` /
`hasPreviousData` / `summary`。

### M.1 功能目标

回答一个问题：**我的钱通常在什么时候花掉？**

这是系统里唯一按"时间"维度做的分析。三条硬性边界：

1. **不是预测**：只描述目标月已经发生的消费，不做任何外推，不产生未来数字；
2. **不依赖预算**：没有设置预算也能正常使用；
3. **不使用历史月份**：只读取目标月本身（当月 1 日 ~ 月末），与 4-A / 4-D 的多月口径完全不同。

输出六项可复核的结论：

| 指标 | 说明 |
| --- | --- |
| 星期分布 | 周一 ~ 周日的支出金额与占比（固定 7 项，即使某天为 0 也返回） |
| 月内阶段分布 | 1-10 日 / 11-20 日 / 21 日-月底（固定 3 项） |
| 消费集中度 | 最高星期金额占总支出的比例 |
| 峰值星期 | 金额最高的星期（并列时按周一 → 周日顺序取第一个） |
| 峰值阶段 | 金额最高的月内阶段 |
| 记账覆盖率 | 有支出的天数占当月天数的比例（用于自查数据完整性） |

### M.2 与 4-A ~ 4-D 的边界

| 模块 | 回答问题 | 时间方向 | 依赖预算 | 数据窗口 |
| --- | --- | --- | --- | --- |
| 4-A 智能预算预测 | 这个月会不会超预算 | 本月 → 月末 | **是** | 本月 |
| 4-B 周期性支出识别 | 哪些支出会重复 | 过去 → 模式 | 否 | 最近 180 天 |
| 4-C 消费异常检测 | 哪里偏离历史常态 | 本月 vs 前 3 月 | 否 | 目标月 + 前 3 月 + 前 90 天 |
| 4-D 智能下月支出预估 | 下个月大概花多少 | 本月 → 下月 | 否 | 参考月前 6 个完整月 + 参考月 |
| **4-E 消费节奏分析** | **钱什么时候花掉** | **本月（不跨月）** | 否 | **只读目标月** |

### M.5 算法设计

**统计口径**：只统计 `type=1`（支出）且当天合计金额 > 0 的日期；收入（`type=2`）与不计收支（`type=3`）不参与；
同一天出现多行时金额合并，且只算作一个消费日。

**星期分布**：按 `LocalDate.getDayOfWeek()` 归类，返回固定 7 项（周一 = 1 … 周日 = 7），
每项包含金额与占比：

```text
星期占比 = 该星期支出金额 ÷ 当月总支出 × 100
```

**月内阶段分布**：按日期所在区间归类，返回固定 3 项：

```text
第一阶段：1 ≤ day ≤ 10        第二阶段：11 ≤ day ≤ 20        第三阶段：21 ≤ day ≤ 当月天数
第三阶段的 endDay 随当月天数变化（28 / 29 / 30 / 31 天都正确）
阶段占比 = 该阶段支出金额 ÷ 当月总支出 × 100
```

**记账覆盖率**：

```text
覆盖率 = coveredDays ÷ daysOfMonth × 100      （coveredDays = 有支出记录的天数）
```

**消费集中度**：

```text
集中度 = maxWeekdayAmount ÷ totalAmount × 100 （maxWeekdayAmount = 金额最高星期的支出）
```

**峰值**：取金额最高的星期与阶段；金额并列时按"周一 → 周日"顺序取第一个，保证同一份数据的结果稳定。

**百分比口径**：每项独立按 `part × 100 ÷ total` 四舍五入到两位小数，不做"末位补差"，
因此 7 项或 3 项之和在极端情况下可能是 99.99 / 100.01（各项都能独立复核）。

### N.1 功能目标

回答一个问题：**我的钱主要花给谁了？**

这是系统里唯一按「消费对象（交易对象）」维度做的分析，与已有的五个模块形成互补：

| 模块 | 回答的问题 | 分析维度 |
| --- | --- | --- |
| 4-A 智能预算预测 | 这个月会不会超预算 | 预算 |
| 4-B 周期性支出识别 | 哪些支出会重复 | 商户（看间隔是否规律） |
| 4-C 消费异常检测 | 哪里偏离历史常态 | 分类 / 单笔 |
| 4-D 智能下月支出预估 | 下个月大概花多少 | 月度总量 |
| 4-E 智能消费节奏分析 | 钱什么时候花掉 | 时间（星期 / 月内阶段） |
| **4-F 消费对象分析** | **钱花给谁** | **消费对象（金额结构）** |

三条硬性边界：

1. **不是预测**：只描述目标月已经发生的支出分布，不产生任何未来数字；
2. **不依赖预算**：没有设置预算也能用；
3. **不使用历史月份**：只分析目标月本身（与 4-E 口径一致）。

### N.2 与既有能力的边界（为什么不是重复）

| 对比对象 | 4-F 与它的区别 |
| --- | --- |
| 4-B 周期识别 | 4-B 用商户是为了判断"间隔是否规律"，只输出有周期性的商户（180 天窗口）；4-F 统计的是**当月全部消费对象**的金额结构，不做任何周期判断 |
| 4-C 单笔异常 | 4-C 返回商户只是为了给异常单笔做定位；4-F 不判断异常，只做金额排行 |
| 统计页「分类统计」 | 那是**分类**维度（固定 10 类）；4-F 是**消费对象**维度（实测平均 6.13 个/用户，比分类更细） |
| 统计页「来源统计」 | 那是**支付渠道**维度（微信 / 支付宝 / 手动） |

### N.4 数据流程

```text
统计页（选中月份）
        ↓  InsightService.merchants(month)
InsightsController  GET /api/insights/merchants?month=yyyy-MM
        ↓  CurrentUser.get() 取得 userId
SpendingMerchantService.analyze(userId, month)
        ↓  参考月 ≠ 当前月 → 直接返回 NOT_APPLICABLE（不查库）
BillMapper.selectExpenseDetails(userId, type=1, 当月 1 日, 当月月末, LIMIT 2000)   ← 复用 4-C 引入的方法
        ↓  内存：过滤金额 ≤ 0 的脏数据 → 按归一化商户聚合金额与笔数
排序（金额↓ → 笔数↓ → 名称↑）→ Top5 → 集中度 / 客单价 / 覆盖率 / 未填写统计
        ↓
SpendingMerchantResponse → MerchantSection / MerchantCard 展示
```

状态判定顺序（只依赖这一次查询的结果）：

```text
参考月 ≠ 当前月                          → NOT_APPLICABLE（0 次查询）
当月支出合计 = 0                         → NO_DATA（1 次查询）
消费天数 < 3 或 有效对象 < 2 或 覆盖率 < 50%  → INSUFFICIENT_DATA（1 次查询，事实数据如实返回）
否则                                     → OK
```

### N.5 算法设计

**统计口径**：只统计 `type=1` 且金额 > 0 的记录；收入与不计收支不参与；明细为 null 或金额为 null 的记录跳过。

**商户清洗（只做三件事）**：

```text
分组键 = trim(商户名) → 把连续空格压缩为一个空格 → 统一小写
展示名 = trim(商户名) → 压缩连续空格（保留用户第一条记录的写法）
```

刻意**不剥离"店 / 旗舰店 / 有限公司"等后缀、不做同义词合并**：4-B 的教训是过度合并会把
不同门店错误地算成一个对象（例如「星巴克」与「星巴克店」必须保持为两个对象）。

**聚合**：按分组键累计金额与笔数；商户为空（null / 空串 / 纯空格）单独计入"未填写"，不混进任何对象。

**排序（三条固定规则，保证结果稳定）**：

```text
金额降序 → 笔数降序 → 名称字典序升序
```

**指标**：

```text
averageAmount      = totalAmount ÷ totalCount                       （整体客单价）
merchantCoverage   = 填写了交易对象的笔数 ÷ totalCount × 100          （覆盖率，笔数口径）
unknownMerchantRate= unknownMerchantAmount ÷ totalAmount × 100       （未填写金额占比）
top3Concentration  = Top3 消费对象金额合计 ÷ totalAmount × 100        （集中度）
单项 percentage    = 该对象金额 ÷ totalAmount × 100
```

**排行上限**：最多返回 5 项（后端截断），前端再做一次 5 条保护。

### N.6 API 设计

```text
GET /api/insights/merchants?month=yyyy-MM
```

| 项 | 说明 |
| --- | --- |
| 鉴权 | 复用 `AuthInterceptor` + JWT，未登录 401 |
| 用户隔离 | `userId` 只来自 `CurrentUser.get()`，方法签名不接受 `userId` |
| 参数 | `month`（参考月）必填，格式 `yyyy-MM`；空值与格式错误（如 `2026-9`、`abc`）→ 400 |
| 范围 | 只分析目标月本身；非当前月份返回 `NOT_APPLICABLE`（HTTP 200，不是错误） |

响应结构：

```text
SpendingMerchantResponse
├── month                  参考月（yyyy-MM）
├── status                 OK / INSUFFICIENT_DATA / NO_DATA / NOT_APPLICABLE
├── message                中文说明
├── totalAmount            当月支出合计
├── totalCount             当月支出笔数
├── averageAmount          整体客单价
├── merchantCount          有效消费对象数量
├── merchantCoverage       交易对象覆盖率（%）
├── unknownMerchantAmount  未填写交易对象的支出合计
├── unknownMerchantRate    未填写交易对象的金额占比（%）
├── top3Concentration      Top3 消费对象金额集中度（%）
├── summary                一句话结论（非 OK 时为空串）
└── topMerchants           最多 5 项 [{merchantName, amount, count, percentage}]
```

四种状态的页面表现：

| status | 判定条件 | 页面表现 |
| --- | --- | --- |
| `OK` | 有支出天数 ≥ 3 且对象 ≥ 2 且覆盖率 ≥ 50% | 对象排行 + 集中度 + 客单价 + 覆盖率 + 一句话结论 |
| `INSUFFICIENT_DATA` | 有支出，但天数 / 对象数 / 覆盖率任一不足 | 「消费记录不足，记录更多消费对象后即可分析」+ 已支出金额与笔数 |
| `NO_DATA` | 当月支出合计为 0 | 「本月暂无支出记录」 |
| `NOT_APPLICABLE` | 参考月不是当前月 | 「该月份不支持消费对象分析」 |

### N.7 Flutter 设计

统计页区块顺序（在既有顺序中插入一个区块）：

```text
本月概览 → 预算卡 → 智能预算预测 → 周期性支出提醒 → 消费异常提醒 → 下月支出预估
→ 本月消费洞察 → 分类统计 → 来源统计 → 消费对象分析（新增） → 消费节奏分析 → 趋势图
```

**首页不接入**（前端接入阶段实测：统计页此时已有 12 个区块、11 个请求，首页保持 6 个区块不变）。

页面表现：

| 状态 | UI |
| --- | --- |
| `loading` | 「正在分析消费对象…」+ 转圈（区块独立 loading） |
| `error` | 统一中文提示 + 「重试」按钮，失败只隐藏本区块 |
| `OK` | 副标题「看看你的钱主要花给谁」→ 总览三列（本月支出 / 消费笔数 / 平均客单价）→ 覆盖率提示 → 消费对象排行（最多 5 条：名次 + 名称 + 金额 + 条形 + 「笔数 · 占比」，前 3 名用品牌橙加粗）→ Top3 集中度 → 未填写提示（占比 > 0 时才显示）→ 后端一句话总结 |
| `INSUFFICIENT_DATA` | 引导文案 + 已有金额与笔数 |
| `NO_DATA` | 引导文案 |
| `NOT_APPLICABLE` | 「该月份不支持消费对象分析」+「统计分析仅针对当前月份」（提示状态，不使用错误图标） |

金额全部走 `Money.format`（字符串 + 整数分）；条形宽度只由百分比换算，不参与金额计算；
颜色只使用既有 `Brand.orange` / `Brand.green` 与中性灰，不新增颜色、字体与依赖。

### N.10 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| 1 | **明细上限 `LIMIT 2000`** | 单月支出超过 2000 笔（≈67 笔/天）时只分析最近 2000 笔，页面显示的总额与对象数只覆盖这部分数据；这是与 4-C 相同的既有保护策略 |
| 2 | **展示名取"第一条记录"的写法** | 分组键统一小写，展示名保留首次出现的大小写（`Starbucks` 而非 `starbucks`），取决于查询顺序（最近一条） |
| 3 | **刻意不做商户合并** | `星巴克` 与 `星巴克店` 会算作两个对象，品牌同一但写法不同的场景会分散统计 |
| 4 | **覆盖率是笔数口径** | `merchantCoverage` 为"有对象的笔数 ÷ 总笔数"，与金额口径的 `unknownMerchantRate` 不同，页面上两者都会展示 |
| 5 | **`INSUFFICIENT_DATA` 有三重门槛** | 消费天数 < 3、对象 < 2、覆盖率 < 50% 任一命中就不给排行；门槛值集中定义在常量里 |
| 6 | **非当前月份一律 NOT_APPLICABLE** | 与 4-A / 4-D / 4-E 保持一致 |
| 7 | **不做任何预测** | 只描述当月已发生的消费对象结构，不推断未来月份的消费去向 |
| 8 | **没有人工截图的视觉确认** | 受执行环境限制（浏览器自动化不可用），前端渲染正确性由「真实后端数据 + Widget 渲染断言」覆盖 |
