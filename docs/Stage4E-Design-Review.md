### 1.2 四个模块共同遵守的约束（Stage 4-E 必须延续）

1. **数据库零变化**：至今仍是 4 张表（`user` / `bill` / `budget` / `import_batch`）与 13 个索引对象（含主键）；
2. **用户隔离**：`userId` 一律来自 `CurrentUser.get()`，方法签名不接受 `userId`；
3. **可解释**：每条结论都能用手工算式复核，不使用黑盒模型；
4. **不引入外部依赖**：不调用任何大模型 API，不新增第三方库；
5. **结果不落库**：全部实时计算，失败只影响自己所在的区块。

| `type=1` 支出 | **2754 条 / 105 个用户** |
| `type=2` 收入 | **67 条 / 35 个用户** ← 关键反证数据 |

### 2.3 推荐选题：C1「消费节奏与时间分布分析」

一句话：回答"**我的钱在什么时候花掉的**"，把系统的分析维度从「金额 / 分类 / 月份」扩展到「时间结构」。

拟输出（全部可由用户手工复核）：

1. **周内分布**：周一至周日的支出金额与占比（例："61% 的支出发生在周末"）；
2. **月内阶段分布**：每月 1–10 日 / 11–20 日 / 21 日–月末三段的金额与占比（例："每月前 10 天花掉 45%"）；
3. **消费集中度**：支出最高的星期与月内阶段，以及相对"平均线"的倍数；
4. **记账覆盖度**：窗口内有多少天存在支出记录（用于自我校验，也解释占比为什么会失真）。

选择它的四条理由：

1. **维度全新**：4-A 看"本月速度"、4-B 看"商户重复"、4-C 看"分类偏离"、4-D 看"下月总量"，没有一个是"什么时候花"；
2. **数据现成**：`BillMapper.sumByDay(userId, start, end)` 已存在且接受任意区间，**一次查询即可覆盖 6 个完整自然月**（每月最多 31 行，合计 ≤186 行）；
3. **零结构变化**：不需要新表、新字段、新索引，理想情况下也不需要新 Mapper 方法；
4. **可解释、好演示**：所有结论都是"金额 ÷ 总额"的百分比，答辩现场可以拿真实账单当场手算复核。

## 3. Push Back（本阶段最重要的部分）

### 3.1 反对"再做一个消费预测"

已有 4-A（本月月末预测）与 4-D（下月总量预测）。再加任何"预测未来金额"的能力，都是**同一个问题的第三遍**：

| 候选 | 与谁重复 | 裁决 |
| --- | --- | --- |
| 未来 7 天预估 | 4-A（同一条"日均外推"公式，只是换了区间） | **延期** |
| 分类级下月预估 | 4-D（同源，只是把总量拆到分类） | **延期**（先解决单分类样本稀疏的前提） |
| "月末还剩多少"之类 | 4-A 的 `daysLeft` / `projectedOver` | 不新增 |

若在统计页并排放两个含义相近的预测数字，用户无法分辨，答辩时也说不清区别。

### 3.2 反对"用评分包装已有结论"（C6 REJECT）

财务健康评分看起来"很智能"，但它本质是把 4-A 的预算使用率、4-C 的异常条数、4-D 的波动幅度加权求和：

1. **权重没有客观依据**（为什么结余占 40%？），无法回答"这个分数怎么算出来的"；
2. **输入不齐**：只有 47 / 215 的用户设置了预算，缺项时评分要么失真、要么需要"按比例折算"，规则越滚越复杂；
3. **与已有结论重复**：用户已经能看到"预算已用 86%""本月有 2 处异常"，再给一个 78 分没有新增信息。

### 3.3 数据反证：收入侧能力（C4）在本项目**不成立**

最初看起来最"理所当然"的空白是**收入侧**——四个智能模块全部只看 `type=1`，
没有任何能力回答"我这个月能存下多少"。但实测数据不支持：

| 证据 | 数值 |
| --- | --- |
| 收入账单总量 | 67 条 |
| 有收入记录的用户 | 35 / 215（**16%**） |
| 收入记录的来源 | 只出现在最近两个月，且全部由自动化测试写入 |
| 历史最深的用户（124 条 / 7 个月） | 收入记录 **0** 条 |

也就是说，**84% 的用户打开这个功能只会看到"暂无收入记录"**，结余率无法计算，答辩演示里这个模块基本是空的。
除非先解决"用户愿不愿意记收入"这个产品问题，否则结论是 **REJECT（数据不支持）**——
不是"暂时不做"，而是当前数据下**做出来没有用**。

### 3.4 反对需要新表的方向（C7 REJECT）

标签体系 / 储蓄目标 / 多账户都需要新增表或字段，而项目从 Stage 4-A 起就确立了"智能能力不改变数据库结构"的约束：

1. 数据库结构变更会让前面所有阶段的验证结论（4 张表 / 13 个索引）失效，必须重跑全链路验证；
2. 这些属于**记账维度扩张**，不是**智能能力**，与 Stage 4-E 的定位不符；
3. 当前痛点不是"缺少记账维度"，而是"缺少对已有数据的深度解读"。

### 3.5 反对引入大模型与机器学习（C8 REJECT）

| 方案 | 否决理由 |
| --- | --- |
| LLM 财务建议（DeepSeek / OpenAI 等） | README 与 Stage 3 起的所有阶段都明确"不接入大模型"；还会带来 API Key 管理、超时降级、费用与数据出境问题，输出不可复核 |
| ARIMA / Prophet / LSTM / XGBoost | 现实数据只有 3~7 个月（单用户最多 124 条），长序列模型在这点数据上等于过拟合；且需要一个 Python 服务，破坏 Spring Boot 单体架构 |
| 向量库 / Embedding / RAG / Agent | 与"个人记账 + 本科毕业设计"的规模完全不匹配，纯增加答辩风险 |

结论：Stage 4-E 必须是**确定性、可手工复核的统计方法**。

### 3.6 反对"重复展示"式交付（C5 不推荐作为主体）

月度报告技术上最省事（把已有四个模块的结论再排版一次），但没有新增任何计算，
答辩时很难回答"这一阶段的贡献是什么"。除非明确需要"报告类"交付物，否则不建议作为主体。

### 3.7 对"统计页信息过载"的提醒

统计页当前已有 **9 个区块**（概览 → 预算卡 → 预算预测 → 周期 → 异常 → 下月预估 → 洞察 → 分类 → 来源 → 趋势），
首页已有 6 个区块 / 7 个请求。Stage 4-E 若再往统计页加内容，页面会更长，因此本报告对前端提出硬性要求：

> **只新增 1 个紧凑区块，放在事实统计区；首页不新增任何内容。**

## 5. API 设计草案（只设计，不实现）

### 5.1 路径与归属

```text
GET /api/insights/rhythm?month=yyyy-MM
```

放在 `/api/insights` 家族的理由：与 4-B / 4-C / 4-D 一样属于"对已有账单做的推断型分析"，
统一返回 `status` + `message` + 可解释依据；`/api/statistics/*` 家族保持"纯事实汇总"的语义不变。

### 5.2 请求

| 项 | 说明 |
| --- | --- |
| 鉴权 | 复用 `AuthInterceptor` + JWT；未登录 401 |
| 用户隔离 | `userId` 只来自 `CurrentUser.get()`，**不接受前端传入 `userId`** |
| 参数 | `month`（参考月）必填，格式 `yyyy-MM`；空值 / 格式错误 → 400 |
| 范围 | 只对「参考月 = 当前月」返回结论；过去与未来月份 → `NOT_APPLICABLE`（与 4-A / 4-D 一致） |
| 分析窗口 | 参考月之前的 **6 个完整自然月**（默认，与 4-D 的读取窗口口径一致，便于复用同一套"完整月"概念） |

### 5.3 响应草案

| 字段 | 说明 |
| --- | --- |
| `month` | 参考月 |
| `status` | `OK` / `INSUFFICIENT_DATA` / `NO_DATA` / `NOT_APPLICABLE` |
| `message` | 中文说明 |
| `windowMonths` | 参与统计的完整月数（6） |
| `windowStart` / `windowEnd` | 窗口起止日期（yyyy-MM-dd） |
| `totalAmount` | 窗口内支出合计 |
| `activeDays` | 有支出记录的天数 |
| `coveredMonths` | 有支出的月份数 |
| `weekdayItems[]` | 7 项：`weekday`(1–7) / `label`(周一…周日) / `amount` / `percentage` / `activeDays` |
| `periodItems[]` | 3 项：`period`(`EARLY`/`MIDDLE`/`LATE`) / `label`(1–10 日 / 11–20 日 / 21 日–月末) / `amount` / `percentage` |
| `peakWeekday` | 支出最高的星期：`weekday` / `label` / `percentage` / `multiple`（相对 1/7 平均线的倍数） |
| `peakPeriod` | 支出最高的月内阶段：`period` / `label` / `percentage` / `multiple`（相对 1/3 平均线） |
| `summary` | 一句话结论（例："你的支出集中在周末，占 61%"） |

### 5.4 状态枚举

| 状态 | 判定条件（草案） | 页面表现 |
| --- | --- | --- |
| `OK` | 有支出，且 `activeDays ≥ 20` 且 `coveredMonths ≥ 2` | 展示周内分布 + 月内阶段分布 + 峰值 + 覆盖度 |
| `INSUFFICIENT_DATA` | 有支出，但记账天数或月份数不足 | 「记账天数还太少，多记几天后可以看出消费节奏」+ 已有事实值 |
| `NO_DATA` | 窗口内没有任何支出 | 「还没有支出记录」 |
| `NOT_APPLICABLE` | 参考月不是当前月 | 「消费节奏分析只对当前月份有效」 |

> 阈值（20 天 / 2 个月）是**草案值**，Step 2 需要结合实现与测试最终冻结；冻结后写入设计文档附录。

## 6. 前端设计草案

### 6.1 放在哪里

| 候选位置 | 评估 |
| --- | --- |
| 首页 | **否决**：首页已有概览 + 环比 + 预算预测；节奏分析属于"深度解读"，放首页会加剧信息过载 |
| 独立页面 | **否决**：为一个区块新增页面，与"最小增量"原则冲突，也不利于答辩演示路径的连贯性 |
| 统计页顶部（与预测区块并排） | 不采纳：会让"预测 / 提醒"区域越堆越长 |
| **统计页事实统计区（推荐）** | 位置：**来源统计之后、趋势图之前**。理由：它与分类统计、来源统计、趋势图同属"描述性事实"，放在一起阅读路径自然；且不打断上方"提醒 → 预测 → 洞察"的分析主线 |

最终顺序：

```text
本月概览 → 预算卡 → 智能预算预测 → 周期性支出提醒 → 消费异常提醒 → 下月支出预估
→ 本月消费洞察 → 分类统计 → 来源统计 → 消费节奏分析（新增） → 趋势图
```

### 7.3 真实接口验证（新建 `spending_rhythm_integration_test.dart`，后端未启动自动 skip）

1. 构造一个账号，把某个完整月的所有支出都放在**周六**（约 10 笔）→ 断言周内分布中周六占比最高、月内阶段落在"21 日–月末"或指定段；
2. 构造三个月、每天各一笔的账号 → 断言七个星期的占比接近 14.3%、三段占比接近 33%；
3. 空账号 → `NO_DATA`；只有 2 天记录的账号 → `INSUFFICIENT_DATA`；
4. 历史月份与未来月份 → `NOT_APPLICABLE`；
5. 用户隔离：A 有数据、B 为空 → B 看不到 A 的分布；
6. 用真实返回数据渲染区块（断言标题、summary 与两个分布区域）。

### 7.4 性能验证

沿用 Stage 4-D 的方法：临时账号灌入约 12000 条账单（覆盖 7 个自然月），
预热后采样 ≥20 次记录 median / avg / max，并**从后端 SQL 日志确认单次请求只执行 1 条 SQL**；
验证结束后删除临时账号与账单，不污染开发数据。
