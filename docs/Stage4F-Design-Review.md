## 1. 能力盘点

### 1.1 已有五个智能模块

| 模块 | 回答的问题 | 分析维度 | API | 依赖预算 | 数据窗口 | 新表 |
| --- | --- | --- | --- | --- | --- | --- |
| 4-A 智能预算预测 | 这个月会不会超预算 | 预算 | `GET /api/budgets/predictions` | **是** | 本月 | 无 |
| 4-B 周期性支出识别 | 哪些支出会重复发生 | 商户（周期性） | `GET /api/insights/recurring` | 否 | 最近 180 天 | 无 |
| 4-C 消费异常检测 | 本月哪里偏离常态 | 分类 / 单笔 | `GET /api/insights/anomalies` | 否 | 目标月 + 前 3 月 + 前 90 天 | 无 |
| 4-D 智能下月支出预估 | 下个月大概花多少钱 | 月度总量 | `GET /api/insights/forecast` | 否 | 参考月前 6 个完整月 + 参考月 | 无 |
| 4-E 消费节奏分析 | 钱什么时候花掉 | 时间（星期 / 月内阶段） | `GET /api/insights/rhythm` | 否 | 只读目标月 | 无 |

五个模块的共同约定（Stage 4-F 必须延续）：

1. **数据库零变化**：4 张表 / 13 个索引对象；不新增表、字段、索引；
2. **用户隔离**：`userId` 只来自 `CurrentUser.get()`，方法签名不接受 `userId`；
3. **可解释**：每条结论都是可手工复核的算式，不使用黑盒模型；
4. **实时计算、不落库**；失败只影响自己所在的区块；
5. **无外部 AI 依赖**。

| 能力 | 需要的数据 | 实测 | 结论 |
| --- | --- | --- | --- |
| 收入侧结余 / 储蓄能力 | 稳定的收入记录 | 收入仅 71 条、37/233 用户（16%），且全部来自自动化测试 | **REJECT**：84% 的用户只会看到"暂无收入记录" |

| 标签体系 / 储蓄目标 / 多账户 | 新表 + 新字段 | — | **REJECT**：违反"数据库零变化"，且会让前五个阶段的验证结论失效 |

又有 6 倍于分类数的对象数量，且前五个模块从未按这个维度回答过问题。

## 3. 候选能力分析

### 候选 1（推荐）：消费对象分析 —— 我的钱花给谁了

- **用户问题**：这个月我把钱花在哪些地方了？是不是集中在少数几个商户？每个商户我平均花多少？
- **输入数据**：`bill` 当月的支出明细（`merchant` / `amount` / 日期），复用 `BillMapper.selectExpenseDetails(userId, type=1, 当月1日, 当月月末, 2000)`。
- **是否需要新表**：**否**。
- **是否需要新 Mapper**：**否**（复用 4-C 已引入的 `selectExpenseDetails`，一次查询）。
- **是否与已有能力重复**：**低**。4-B 用商户是为了找"周期性间隔"；4-C 返回商户只是为了定位异常单笔；统计接口的「分类统计」「来源统计」是分类与支付渠道维度。**"按商户排行的金额结构"从未出现过**。
- **数据是否支持**：**支持**。96.1% 的支出账单有商户，平均 6.13 个商户/用户（最多 17 个）。
- **答辩价值**：**高**。"我的钱花给谁了"是所有记账类产品的核心问题之一，结论直观、图表好画、可现场用真实账单核对。
- **风险**：商户名不规范（导入数据可能带平台前缀或分店后缀）需要最小归一化；手工记账不填商户时要如实展示"未填商户"的占比，不能假装覆盖完整。

### 候选 2：分类份额演变（近 6 个月结构变化）

- **用户问题**：我的消费结构在怎么变？哪一类占比在上升？
- **输入数据**：`sumByCategoryAndMonth`（一次查询，6 个月）。
- **是否需要新表**：否。
- **是否需要新 Mapper**：否。
- **是否与已有能力重复**：**中**。与 4-C 落在同一维度（分类）：4-C 比较"金额 vs 3 月基线"，本候选比较"份额随月份的变化"。区别存在，但答辩时容易被问"这跟异常检测有什么不同"。
- **数据是否支持**：**弱**。实测**平均只有 2.71 个分类/用户**，多数用户的"结构"只有两三类，"演变"没有信息量。
- **答辩价值**：中（可视化好看，但样本薄）。
- **风险**：分类数太少导致结论不稳定；与 4-C 的边界需要反复解释。

### 候选 3：刚性 vs 弹性支出结构

- **用户问题**：我的钱有多少是"不得不花"的？可压缩空间有多大？
- **输入数据**：按分类汇总（一次查询），再按固定规则分为刚性（餐饮 / 交通 / 住宿 / 医疗 / 通讯）与弹性（购物 / 娱乐 / 学习 / 生活 / 其他）。
- **是否需要新表**：否。
- **是否需要新 Mapper**：否。
- **是否与已有能力重复**：低（新维度：支出性质）。
- **数据是否支持**：**弱**。同样受"平均 2.71 个分类/用户"限制；而且实测数据显示分类高度集中在餐饮 / 购物两类，刚性弹性的对比会退化成"两类占比"。
- **答辩价值**：中高（故事好），但**分组规则带有产品主观判断**（为什么"生活"算弹性），需要额外解释成本。
- **风险**：主观分类可能被质疑；分组规则一旦写死，后续分类调整会连带失效。

### 候选 4：客单价与消费频次画像

- **用户问题**：我一个月花几笔？平均每笔多少钱？哪一类最贵？
- **输入数据**：`sumByCategoryAndMonth`（含 `count`，一次查询）。
- **是否需要新表**：否。
- **是否需要新 Mapper**：否。
- **是否与已有能力重复**：低（新指标：笔数与客单价）。
- **数据是否支持**：支持（笔数、金额都有）。
- **答辩价值**：中。指标清楚但"故事性"弱，更多是数字陈列，缺少可行动的结论。
- **风险**：容易变成"统计接口的又一次展示"；与 4-C 的 `FREQUENCY_SPIKE` 在"笔数"上有轻微重叠。

### 候选 5：记账数据质量与可信度

- **用户问题**：我的记账数据够不够支撑这些分析结论？
- **输入数据**：按天聚合（一次查询）：有记录的天数、连续天数、导入 vs 手动占比、分类缺失比例。
- **是否需要新表**：否。
- **是否需要新 Mapper**：否（复用 `sumByDay`）。
- **是否与已有能力重复**：无。
- **数据是否支持**：支持。
- **答辩价值**：中低。属于"元分析"（分析数据本身），对用户的实际财务决策帮助有限，更适合作为其它模块的可信度标注。
- **风险**：与 4-E 已经输出过的 `coveredDays` / `coveredRate` 部分重合。

### 候选 6：收入侧结余 / 储蓄能力分析

- **用户问题**：我一个月能存下多少钱？
- **输入数据**：`sumByType`（收入 + 支出）。
- **是否需要新表**：否。
- **是否需要新 Mapper**：否。
- **是否与已有能力重复**：无（唯一完全空白的财务维度）。
- **数据是否支持**：**不支持**。收入仅 71 条、37/233 个用户（16%），且全部由自动化测试写入；**84% 的用户打开只会看到"暂无收入记录"**。
- **答辩价值**：理论上最高，实际演示基本是空的。
- **风险**：功能上线后绝大多数用户看不到任何结论，属于"为了完整而完整"。

### 候选 7：同比 / 季度对比

- **用户问题**：我比去年同期多花了吗？
- **输入数据**：12~24 个月的历史聚合。
- **是否需要新表**：否。
- **是否需要新 Mapper**：否（`sumByCategoryAndMonth` 可覆盖任意区间）。
- **是否与已有能力重复**：与 4-D / 统计接口「消费趋势」同源（都是总量对比）。
- **数据是否支持**：**不支持**。平均 2.54 个月、最深 7 个月，同比的分母根本不存在。
- **答辩价值**：低（无法演示）。
- **风险**：算出来的是噪声，会误导用户。

### 候选汇总

| # | 候选 | 数据支持 | 与已有重复 | 新表 | 新 Mapper | 裁决 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 消费对象（商户）分析 | **强** | 低 | 否 | 否 | **推荐** |
| 2 | 分类份额演变 | 弱 | 中 | 否 | 否 | 备选（需先解决分类稀疏） |
| 3 | 刚性 / 弹性结构 | 弱 | 低 | 否 | 否 | 备选（主观分组） |
| 4 | 客单价与频次画像 | 强 | 低 | 否 | 否 | 备选（故事性弱） |
| 5 | 记账数据质量 | 强 | 无 | 否 | 否 | 不建议（元分析） |
| 6 | 收入侧结余 / 储蓄 | **不支持** | 无 | 否 | 否 | **REJECT** |
| 7 | 同比 / 季度对比 | **不支持** | 中 | 否 | 否 | **REJECT** |

## 4. Push Back（明确拒绝的方向）

### 4.1 只是已有能力换皮 → REJECT

| 被拒方向 | 为什么是换皮 |
| --- | --- |
| 再做一次"本月预计支出" | 4-A 的 `projected` 已经给出 |
| 再做一次"下月总量" | 4-D 的 `predictedAmount` 已经给出 |
| 再做一次"分类金额 vs 基线" | 4-C 的 `CATEGORY_SPIKE` 已经给出 |
| 把现有结论重新排版成"月报/仪表盘" | 没有新增任何计算，属于 UI 重构而非新能力 |
| 把 4-E 的星期分布与分类交叉成"周末餐饮" | 与 4-E 同维度，属于换皮（可作为 4-E 的后续深化，不是新 Stage） |

### 4.2 需要大量历史数据 → REJECT

同比（YoY）、季度对比、季节性分析都需要 12~24 个月；实测**平均只有 2.54 个月、最深 7 个月**，
分母不存在，算出来的只能是噪声。

### 4.3 需要机器学习但数据不足 → REJECT

ARIMA / Prophet / LSTM / XGBoost 需要数十个稳定观测点，当前规模下等于过拟合；
还要引入 Python 服务，破坏 Spring Boot 单体架构与"可解释"原则。

### 4.4 需要新增复杂表结构 → REJECT

标签体系、储蓄目标、多账户、商户维表都需要新表/新字段：

1. 会让 Stage 4-A ~ 4-E 已验收的"4 张表 / 13 个索引对象"结论失效，必须重跑全链路验证；
2. 它们属于**记账维度扩张**，不是**智能分析能力**；
3. 当前痛点不是"缺记账维度"，而是"已有数据还没被充分利用"（96.1% 的商户字段几乎没被消费）。

### 4.5 只是 UI 展示，没有新计算价值 → REJECT

任何"把已有数字换个卡片排版"的方案都不构成一个 Stage。

### 4.6 数据本身不支持 → REJECT

收入侧结余 / 储蓄能力（84% 用户无收入记录）、同比（历史不足）属于此类：
**不是"暂时不做"，而是当前数据下做出来没有用**。

### 4.7 不为凑 Stage 数量而设计

本报告给出 7 个候选，其中 **2 个明确 REJECT、3 个降级为备选**，只推荐 1 个。
推荐理由不是"要凑到 Stage 4-F"，而是：**商户维度是唯一同时满足"数据充足（96.1% 覆盖 / 6.13 个对象）
+ 五个已有模块从未回答 + 零库表变化 + 一次查询"的空白方向**。

## 5. 推荐最终方向

## 主方案：消费对象分析（商户维度）——「我的钱花给谁了」

### 5.1 与其它候选的对比

| 评价维度 | **C1 消费对象** | C2 分类份额演变 | C3 刚性/弹性 | C4 客单价频次 | C5 数据质量 |
| --- | --- | --- | --- | --- | --- |
| 数据库零变化 | 是 | 是 | 是 | 是 | 是 |
| 一次查询 | **是**（复用 `selectExpenseDetails`） | 是 | 是 | 是 | 是 |
| 需要新 Mapper | **否** | 否 | 否 | 否 | 否 |
| 数据支持 | **强**（96.1% / 6.13 个商户） | 弱（2.71 个分类） | 弱（2.71 个分类 + 主观分组） | 强 | 强 |
| 可测试 | 是 | 是 | 是 | 是 | 是 |
| 可解释 | **完全可解释**（金额 ÷ 笔数 ÷ 总支出） | 是 | 分组规则需解释 | 是 | 是 |
| 与 4-A~4-E 的差异 | **明显**（对象维度，从未出现） | 中（同分类维度） | 中（新维度但依赖分类） | 中低 | 明显但价值弱 |
| 答辩展示价值 | **高**（"钱花给谁"直击痛点） | 中 | 中高 | 中 | 中低 |

### 5.2 为什么它比其它候选更适合当前项目

1. **数据反证指向它**：唯一一个有 96.1% 字段覆盖率、且对象数量（6.13）远多于分类数（2.71）的维度；
2. **与五个模块正交**：4-A 预算、4-B 周期、4-C 异常、4-D 未来总量、4-E 时间分布，**没有一个是"对象维度"**；
3. **零成本复用**：`BillMapper.selectExpenseDetails` 已存在且带 `start` / `end` 与 `LIMIT`，一次查询即可覆盖当月；
4. **结论可复核**：每个商户的金额、笔数、占比、客单价都能用原始账单逐条加总验证；
5. **顺带解决一个真实数据问题**：把"未填写商户"的占比显式返回，让用户知道自己的数据完整度
   （实测有 3.9% 的支出账单没有商户）。

### 6.1 API 草案

| 项 | 内容 |
| --- | --- |
| 路径 | `GET /api/insights/merchants?month=yyyy-MM` |
| 归属 | 复用 `InsightsController`（洞察家族，与 4-B / 4-C / 4-D / 4-E 一致：返回 `status` + `message` + 可解释依据） |
| 鉴权 | 复用 `AuthInterceptor` + JWT，未登录 401 |
| 用户隔离 | `userId` 只来自 `CurrentUser.get()`，**不接受前端传入 `userId`** |
| 参数 | `month`（参考月）必填，格式 `yyyy-MM`；空值与格式错误 → 400 |
| 范围 | 只分析目标月本身（当月 1 日 ~ 月末）；非当前月份 → `NOT_APPLICABLE`（HTTP 200，不是错误） |

**状态枚举**：

| 状态 | 判定条件（草案） | 页面表现 |
| --- | --- | --- |
| `OK` | 有支出，且有效商户数 ≥ 2 且商户覆盖率 ≥ 50% | 展示商户排行 + 集中度 + 客单价 |
| `INSUFFICIENT_DATA` | 有支出，但有效商户数 < 2 或商户覆盖率 < 50% | 「商户信息不足，补充交易对象后可以分析消费对象」+ 已有事实 |
| `NO_DATA` | 当月没有任何支出 | 「本月暂无支出记录」 |
| `NOT_APPLICABLE` | 参考月不是当前月份 | 「该月份不支持消费对象分析」 |

**Response 字段（草案，13 个）**：

| 字段 | 说明 |
| --- | --- |
| `month` | 参考月 |
| `status` | 四种状态之一 |
| `message` | 中文说明 |
| `totalAmount` | 当月支出合计 |
| `totalBillCount` | 当月支出笔数 |
| `averageAmount` | 整体客单价（支出合计 ÷ 笔数） |
| `merchantAmount` | 有交易对象的支出合计 |
| `merchantCoverage` | 商户覆盖率（%）：有商户的笔数 ÷ 总笔数 |
| `merchantCount` | 有效商户数（归一化后去重） |
| `uncoveredAmount` | 未填写交易对象的支出合计（数据质量提示） |
| `top3Percentage` | Top3 商户金额占总支出的比例（%） |
| `topMerchants` | 最多 5 项：`{merchant, amount, percentage, billCount, averageAmount}` |
| `summary` | 一句话结论（例："你的支出主要集中在 3 个交易对象，合计占 62%"） |

### 6.2 后端设计

| 层 | 计划 | 说明 |
| --- | --- | --- |
| Service | **新增 1 个** `SpendingMerchantService` | 只负责：取数 → 商户归一化 → 分组聚合 → 排行与集中度 → 文案；不改动任何既有 Service |
| DTO | **新增 2 个** `SpendingMerchantResponse` + `MerchantSpendingItem` | 字段与 6.1 冻结清单一一对应，不增加多余字段 |
| Controller | **修改 1 处** `InsightsController` | 新增第 6 个 GET（`/merchants`），既有 5 个接口路径与语义完全不动 |
| Mapper | **0 新增** | 复用 `BillMapper.selectExpenseDetails(userId, type=1, 当月1日, 当月月末, 2000)`：它已带 `start` / `end` / `LIMIT`，返回 `category / amount / billDate / merchant` |

| 依赖 | **0 新增** | 不引入第三方库、不接入大模型 |

**算法要点（草案）**：

1. **只分析当月**：`[当月 1 日, 当月月末]`，不使用历史月份（与 4-E 口径一致）；
2. **商户归一化**：`trim` → 连续空格压缩为一个空格 → 统一小写；
   **不剥离"店 / 旗舰店 / 有限公司"等后缀**（4-B 的教训：过度合并会误合并不同门店，
   如"如家酒店(光谷店)"与"如家酒店"）；同一商户的不同门店在排行中保持独立；
3. **分组聚合**：按归一化商户聚合金额与笔数；金额为 0 或商户为空的记录单独计入"未填写"桶；
4. **排序**：金额降序 → 笔数降序 → 商户名字典序（保证同一份数据结果稳定）；
5. **集中度**：`top3Percentage = Top3 商户金额 ÷ 当月总支出 × 100`；
6. **客单价**：整体 `averageAmount = 总支出 ÷ 总笔数`；单项 `= 该商户金额 ÷ 该商户笔数`；
7. **百分比**：一律 `part × 100 ÷ total` 四舍五入两位小数（与 4-E 口径一致，不做末位补差）；
8. **上限**：明细复用 `LIMIT 2000`，超出时只分析最近 2000 条并在文档中说明。
